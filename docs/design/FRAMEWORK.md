# docHamster UI framework

The one source for how docHamster looks and behaves. Every page and every module (Belege, Notizen, Ordner, Bank, Einstellungen, later the bank modules from their own repos) is built **only** from the building blocks below. Live samples: `/design/styleguide.html` (section "Framework").

Rules for agents (also in `AGENTS.md`):

1. Read this file before you build UI.
2. Use only these classes and components. No own colours, shadows, button looks or column/window logic in a module.
3. A new building block is made on the long-running branch `lead/framework`, documented here first, then used.
4. Plain CSS and JS without a build step (D-004), split by topic (A216): `public/css/core/*.css` and `public/js/core/*.js` = the framework (base, layout, forms, buttons, menus, lists, windows, menu windows, dialogs, tooltips …), `public/css/modules/*.css` and `public/js/modules/*.js` = one file per module (documents, notes, ocr, updates …). The load order is `config/assets.php` (the styleguide links the same CSS list); a new file goes there. UI strings via `lang/`.
5. **No double-click actions (point 169).** Every action has a visible icon button with a tooltip. The only double-click is on a drag edge (window/column width, pane height): it resets the size – and the reset also has its own icon or way.

## 1. Colours and surfaces

Tokens on `:root` in `css/core/base.css`, light and dark follow the system setting.

| Token | Use |
|-------|-----|
| `--primary` `#ff7622` | Main buttons, active marks, icons in heads. **Filled orange is only ever a button.** |
| `--primary-hover` | Main button on hover |
| `--primary-ink` | Orange text and links on the page background |
| `--secondary` | The dark block behind logo and menu button |
| `--bg`, `--surface` | Page and slightly darker surfaces (menu, strips, rows) |
| `--text`, `--muted`, `--border` | Text, quieter text, lines |
| `--danger`, `--ok`, `--error` | Delete buttons, success, errors |
| `--shadow` | One soft dark shadow for everything that floats: tooltips, menus, dialogs, toasts |
| `--button-shadow` | The shadow under buttons |

Sticky notes keep their own 20 colours (`.note-*`); they are not app colours.

## 2. Buttons

Every `<button>` and `.button` is a button by default. Do not reuse its look for anything else. **This table is the whole set (point 243, A433): no further variants, no local sizes, no inline styles.** `scripts/check-ui.php` (CI, `composer check-ui`) rejects classes no stylesheet knows and every `style` attribute (the CSP `style-src 'self'` blocks them in the browser; computed values are set from script). it also counts framework classes (`css/core`) the styleguide does not show (`--list` names them, goal 0; pure script states are on its short allowlist).

| Kind | Markup | When |
|------|--------|------|
| Main | `<button>` | The one main action of an area |
| Side | `<button class="button-quiet">` | Cancel and side actions; outlined, no fill |
| Delete | `<button class="button-danger">` | Delete only |
| Small | add `button-small` | 40 px instead of 48 px, e.g. in list rows |
| Icon | `<button class="icon-button" aria-label="…" data-tooltip="…">` | Square, icon only, always with tooltip |
| File | `<label class="button button-small file-button" data-tooltip="…"><input class="visually-hidden" type="file" …><x-icon name="upload" />Hochladen</label>` | Picks files and starts at once (point 182, Posteingang head); focus ring on the label, `is-busy` (faded, spinning symbol) while sending |
| Link | `<button type="button" class="button-link" data-tooltip="…">` + small symbol + text | An action inside running text or a subline (point 165.6: "lesen als Tag, Monat, Jahr"); orange text, no frame, underlined on hover |
| Group | `<div class="button-group" role="group" aria-label="…">` around buttons | **Actions** side by side (zoom bar, editor toolbar); rounded only outside, a toggled one `aria-pressed="true"`. A group used as a **choice** is always the Umschalter (point 188.3) |
| Knopfgruppe | in a window toolbar: a single `.icon-button`, or `<span class="switcher is-actions" role="group" aria-label="…">` around buttons/links without button classes | **Actions** in a window toolbar (point 200): the Umschalter's grey rail, no frame, hover a darker grey, never the chosen look. Actions that belong together share one rail ("Neues Dokument" + "Neuer Ordner"); the ⋯ menu stands alone. The Umschalter itself is unchanged |
| Umschalter | `<span class="switcher" role="group" aria-label="…">` around `<button>`s or `<a>`s with `aria-pressed` (no button classes) | The horizontal choice (point 188.2, variant B): one grey rail (`--surface`, 10 px corners, 3 px padding, 2 px gap) with text or icon segments; the chosen one a raised white segment in the marked look (`--mark-surface` / `--mark-shadow`, icon orange); hover a slightly darker grey. Narrow (188.4): the rail fills the width; when it still does not fit, `core/button-choice.js` shows a small `select` in its place (`.is-tight` + `.switcher-select`, measured on every size change of its parent like the bank toolbar) – `data-switch-static` = never (the module has its own narrow form, e.g. a dropdown) |
| Quiet link | `<button type="button" class="button-link is-quiet">` | A side action that should not draw the eye ("Zurücksetzen" in the search panel, 187.4): muted text, orange on hover |
| Quiet red link | `<button type="button" class="button-link is-danger" data-dialog-open="…">` | A destructive side action inside an open row ("Zugang entfernen", point 218): red text, no frame; it always opens a confirm dialog with the red delete button |
| Aktionszeile | `<div class="actions">` around buttons (forms inside allowed) | One row of actions below content (point 243, A432): **all the small size** (40 px, icon buttons 40 × 40) whatever their own class, one even gap, wraps when narrow; **at most one** filled main button, the rest `button-quiet` / `button-danger` / `icon-button` (checked by `scripts/check-ui.php`) |
| Control | `<button type="button" class="control-button" aria-label="…" data-tooltip="…">` | Window controls only (minimise ‹ – one term, A218 –, unfold ›, maximise, close): **no frame**, icon in text colour, orange on hover; 36 px in window heads. The menu arrow is its 48 px flavour (points 70, A116) |

48 px high (small 40 px), 10 px corners (icon buttons too, link or button), semi-bold, no letter spacing, light shadow that presses in on click, orange focus ring for the keyboard, faded when disabled. A link stays underlined text and never looks like a button.

**Cursor (A192):** everything clickable shows the hand – one central rule in `css/core/buttons.css` (`:where(…)`, zero specificity): buttons, `.control-button`, icon buttons, row actions, menu entries, links (also whole rows), `summary`, tabs, strips, colour swatches, icon choices, chips, checkbox/radio labels and `select`. Drag edges show `col-resize`, things that move `grab`; disabled things `not-allowed`. Don't set `cursor: pointer` per module.

## 3. Form fields, cards, lists, toasts, dialogs

- **Form field** – label **above** the field (orange, semi-bold), a quiet thin frame, 8 px corners, 48 px high; while typing an orange frame with a soft orange ring; an error gives a thin red frame. The same look for text, password, search, date, number, `select` and `textarea` (grows with its text). Checkboxes, radios, colour and range keep their own look. **Checkbox row (point 217):** `<label><input type="checkbox"> Text</label>` has no top margin (that belongs to a label above a field) and is a compact 36 px row on desktop, the 48 px touch target only under `@media (pointer: coarse)`; a lone checkbox, or the first of a run, after other form parts keeps a .5rem gap, so lists of checkboxes (rights, log books, Belegpaket accounts, filters, dialogs) sit close together. Saved logins (autofill) look like typed text.
  ```html
  <div class="field">
      <label for="username">Benutzername</label>
      <input id="username" name="username" autocomplete="username">
      <p class="field-hint">Optional: a hint below the field.</p>
  </div>
  ```
  An error: `class="field has-error"` (red frame, red hint) or `aria-invalid="true"` on the field. Older forms with the label right before or around the field are drawn the same way; new code uses `.field`.
- **Small field** – `class="input-small"` on an `input` or `select`: 40 px high like small buttons, for tight spots (a search above a list, a field in a row). No label above, a placeholder says what goes in (and `aria-label`). Every `type="search"` field is small by itself.
- **Frame field** – `<fieldset><legend>Tags</legend>…</fieldset>` for a group (tags, checkboxes, colours): no browser frame, the legend stands above like a field's label.
- **Schalter (switch, points 218, 223)** – `<label class="switch"><input type="checkbox" role="switch" name="paused" value="1"> Pausiert</label>` (with a hidden `value="0"` field before it): an on/off that acts at once, inside a `data-autosave` form (Properties module). Off a grey track, on the dark `--secondary` track (never filled orange), white knob; focus ring orange. `data-confirm-title`, `data-confirm-text`, `data-confirm-ok` on the input ask in the framework confirm dialog **before switching on** (`core/switch.js`, capture phase; switching off never asks) – e.g. "Alle 3 Personen mit dieser Rolle werden abgemeldet …". CSS in `core/forms.css`. Use it for states (Pausiert); a list of rights stays checkboxes.

- **Card** – a framed block with a head: `<section class="card"><h2 class="card-head"><x-icon name="…" />Title <form class="card-action">…</form></h2> … </section>`. Text in a card: `.card-text` (readable line length), small print `.card-note`.
- **Card head with action (task 110)** – at most one `form.card-action` at the right end of the head: an icon button (`icon-button`, tooltip) or, for the card's main action, a small button with symbol and text (`<button class="button-small"><x-icon name="refresh" />Update</button>`). Its symbols keep the button's colour. With `data-ajax` the button is busy (`is-busy`: disabled, its symbol spins) until the answer is in.
- **Karte, klappbar (foldable card, point 125, A260/A261)** – `<x-fold-card fold="ocr.mode" :title="…" icon="…" folded summary="App-eigen" summary-tone="ok">…</x-fold-card>` (slot `action` for a `form.card-action`): a card whose head ends in a chevron (`control-button card-fold-button`, `aria-expanded`, tooltip "Aufklappen"/"Zuklappen"; **rule (point 131): the chevron points down while folded = "Aufklappen" and up while open = "Zuklappen"**, every foldable section in the app follows it) that hides the body (`.card-body[hidden]`, the card gets `is-folded`). A folded card shows a short **summary** in its head (`.card-summary`, `is-ok` green check / `is-warning` warning triangle, or `summary-icon`), e.g. "App-eigen ✓", "kein Cronjob ⚠". The page sets the start state (`folded`); what a person folds is remembered **per card id** (`fold="<page>.<card>"`) in the plain cookie `dh_folds` (`core/card-fold.js`, delegated) and the **server draws that state** (`App\Http\CardFolds`), so nothing jumps on load – also in windows loaded later. `DocHamster.foldCard(card, folded)` folds from code; every toggle emits `card:fold { card, folded }`. Use it where a page has several cards and some are rarely needed; a page with one card keeps a plain card. The document detail is all foldable cards (point 185.1): Eigenschaften, GiroCode, Tags, Notiz (`detail.note`, summary = its beginning), Erkannter Text (`detail.ocr`, summary = the recognition state, its tools in an `.ocr-head` row in the body, `data-ocr-card` scopes copy/translate), Verlauf. **Compact variant (point 135):** `<x-fold-card compact …>` (`card-fold is-compact`) for sections inside a panel, e.g. the search panel: no frame, a line below, a small head; the summary shows open and folded (empty = hidden, a module may update `[data-card-summary] > span` live). `:remember="false"` (`data-card-fold-forget`) draws the page's state every time and remembers nothing – e.g. "folded unless a filter in it is set".
- **Optionskarten (option cards, point 188.1)** – the standard **vertical** choice (source: Einstellungen → Geschwindigkeit, Vorladen / Vorschaubilder): `<fieldset class="pick-list option-cards"><legend>…</legend><label class="pick-row"><input type="radio" class="visually-hidden" …><span><strong>Title</strong><small>Description</small></span><span class="pick-mark"><x-icon name="check" /></span></label>…`: grey rows with title and description, the chosen one in the marked look (white, light shadow, 188.5) with the orange check. A few options with a sentence each = Optionskarten; short words side by side = Umschalter.
- **Umschalter als Auswahl (Umschalter as a choice, points 135, 188, A283/A284)** – instead of radios or a select with "egal": `<span class="button-choice" data-choice><input type="hidden" name="match" value=""><span class="switcher" role="group" aria-label="…">` with segments `<button type="button" data-value="…">` (`aria-pressed`); the "Alle" / default option is `data-value=""` and comes first. A click sets the hidden field and `aria-pressed` and sends `change` from the field (`core/button-choice.js`, delegated); `data-choice-toggle` lets a second click on the pressed button set it back to "". After code changed the fields, `DocHamster.syncChoices(root)` makes the buttons follow. Blade in the documents search: `documents/_search-choice.blade.php`.
- **List with rows** – `<ul class="pick-list">` with `<li class="pick-row is-static">` (icon, `<span><strong>…</strong><small>…</small></span>`, optional `pill` labels and a small button on the right; the text part takes the free width, so labels and button line up at the right edge). An empty list shows the **Leerer Zustand** (below) as `<x-empty tag="li" …>`; a not yet loaded list may still show the bare `<li class="list-empty">…</li>`; an error `list-empty list-error`. A row that opens something has its link around the title (`<strong><a href="…" data-window>Name</a></strong>`): **the whole row is the click area**, nothing is underlined or orange, hover darkens the row, the keyboard shows an orange frame around it. Buttons in the row stay clickable on their own.
- **Aufklappliste (accordion list, points 216, 218)** – the settings list whose records are edited in place (Rollen, Personen): `<ul class="accordion-list">` of `<li class="accordion-row">` with `<div class="accordion-head">` holding **one** `<button type="button" class="list-entry accordion-toggle" data-accordion-toggle aria-expanded="false" aria-controls="…">` (row symbol or Initialen-Kreis, `<span><strong>Name</strong><small>a short line</small></span>`, then `<span class="accordion-pills">` with `pill`s on the right – they hide below 30rem window width) and, beside it, an optional `.row-actions` with a `control-button` dropdown (⋯: e.g. "Rolle löschen", red, opening a confirm dialog – or a dialog that explains why it can't be deleted). Below the head `<div class="accordion-body" hidden>`: the record's fields, each saving at once (`form[data-autosave]`, a name with the ✓ of the Feld mit Symbol, checkboxes in `fieldset`s, a foldable card `compact` for rarer parts, a Schalter), label/value lines as `ul.prop-list` > `li.prop-row` (`.prop-name`, `.prop-value`). A click on the head opens the body and closes the other open row of the list (`core/accordion.js`, delegated; event `accordion:toggle { row, open }`); the open row has the white marked look (`.is-open`). The server may draw a row open (`?open=<id>` after a create). A row that can't be opened (Admin, oneself) uses `<span class="accordion-static">` instead of the button. Adding is the Aufklapp-Plus als Zeile above the list. No save button, no stacked form. Reference: `roles/index.blade.php`, `members/index.blade.php`.
- **Initialen-Kreis (initials circle, point 218)** – `<span class="initials">MM</span>` in a person's row instead of a row symbol: the first letters of the first and last name in a 38 px circle, orange tint (`--primary` 16 %) with orange text; `initials is-paused` grey. CSS in `core/lists.css`.
- **Leerer Zustand (empty state, point 213)** – every empty list a person meets says what goes there: `<x-empty icon="inbox" :text="__('empty.inbox')">…button…</x-empty>` (`components/empty.blade.php`, CSS `.empty-state` in `core/lists.css`): the quiet dashed `.list-empty` block with a small orange symbol, **one sentence** (what goes here, and how: "Noch keine Dokumente – hierher ziehen oder hochladen.") and, in the slot, at most one or two fitting buttons on the right (they wrap below on narrow windows). Where the window takes a drop, the sentence is the drop hint and a button is optional. Inside a `<ul>` pass `tag="li"`. Search or filters without a hit use the same block with the `search` / `filter` symbol. The upload button of an empty state is `documents/_upload-button.blade.php` (optional `folder`). Texts in `lang/*/empty.php`. Bare `.list-empty` stays for text-only notes (e.g. "not loaded yet"); Home's widgets use `<x-empty>` too (`.dash-empty` is left only for the photo field).
- **Links** – never underlined, except inside running text (`p`, `.card-text`, hints) – and even there only in rare cases. Lists, heads, menus and tabs never show a link look.
- **Ajax into a card** – `<form data-ajax="#target">`: sends in the background, the controller answers JSON `{html}` with a partial, which replaces `#target`. Without JavaScript the form posts as usual.
- **Marked row (task 110)** – one look for "this one is the current / chosen one": a raised white surface (`--mark-surface`, dark mode a lighter surface) with a light shadow (`--mark-shadow`) and the orange symbol – no bar, no border, no bold text (point 155, variant A3). Used by the current menu entry (`nav-item[aria-current="page"]`), a checked menu entry, a picked choice row (`pick-row:has(input:checked)`) and a marked list row `<li class="pick-row is-static is-marked">` (e.g. the installed version). Not for multi-select (that is `.is-selected`, orange tint). The same look marks the **opener row** of a window (`.is-opener`, set by the window system, § 5).
- **Pill (task 110)** – `<span class="pill">`: the one small round label for states and counts, not clickable. Quiet framed by default ("Vorschau", OCR state, the count in a tab); `pill-ok` green ("installiert"), `pill-new` orange tint ("verfügbar"; also the count of the active tab). Replaces `.tag-outline` and `.tab-count`. `pill-warning` orange and `pill-error` red mark the kind of a log entry (point 115).
- **Errors are logged (point 115)** – server errors and browser errors (uncaught errors, failed promises, a module that throws inside `DocHamster.emit`) land in Einstellungen → Log, logbook "Allgemein", level error (`core/error-report.js`, at most five per page). The event bus never lets one module break another or the window system.
- **Count badge** – `<span class="badge">3</span>`: a round number. Orange; on an `icon-button` it sits on the top right corner (filter count). `badge badge-alert` red, for new things in the main menu (A8–A11). Replaces `.nav-badge`.
- **Toast** – `<div class="toast" role="status" data-toast>…</div>`: top right (on phones at the bottom), closes itself after 5 s.
- **Dialog** – `<div class="dialog-backdrop" data-dialog="name" hidden><div class="dialog" role="dialog" aria-modal="true">…</div></div>`, opened by any `[data-dialog-open="name"]` (also in windows loaded later). `data-dialog-title` on the opener sets `[data-dialog-heading]`. Close: `[data-dialog-close]`, the backdrop, Escape. Names must be unique on the page – put the record's id in them. Asking for the password happens only in the dialog "Bestätigung (Sudo)".
- **Bestätigung (Sudo, point 212, PLAN §11.1 point 6)** – sensitive actions (export, backup, Belegpaket, final delete, roles, people, upload keys, sign-ins, system update) need a confirmation from the last **five minutes**, like GitHub's sudo mode; the sign-in counts. No action has its own password field. Server: the route gets the middleware `confirmed` (`App\Http\Middleware\RequireRecentConfirmation`; the list `ROUTES` is applied at the end of `routes/web.php`, a new route may also write `->middleware('confirmed')`). Nobody without a password is asked (passkey assertion: hook in `App\Domain\Auth\RecentConfirmation::methods()`). Client: one framework dialog `dialog-backdrop[data-confirm-sudo-dialog]` ("Bitte bestätigen", password field, "Bestätigen", X) in the layout, driven by `core/confirm.js`: a **form** with `data-confirm-sudo` asks before it is sent (capture phase, before every module's own submit handler) and is then sent again with the same button (`formaction` kept); **any fetch** answered `423` + header `X-DocHamster-Confirm: required` (JSON `{confirm: true}`) asks and runs the same request again – modules need nothing for it; a plain post that arrives unconfirmed goes back with its input and opens the dialog (`confirm_required`), then a toast says to run it again. `DocHamster.confirmSudo()` → `Promise<boolean>` asks from code. Wrong password: red field frame and the reason below it.
- **Top layer (point 53)** – while shown, dialogs, dropdown panels, toasts and the tooltip lie in the browser's top layer above every window (app.js lifts them as `popover="manual"` when `hidden` goes away): never cut off at a window edge, a dialog's backdrop greys the whole app, later shown = on top. They stay in their place in the DOM, so forms, `closest('section[data-window]')` and per-window names keep working. Just toggle `hidden`; never set `popover` yourself.
- **Dropdown** – `<div class="dropdown"><button type="button" class="icon-button" aria-expanded="false">…</button><div class="dropdown-panel" hidden>…</div></div>`. Works in every window, also in windows loaded later and several side by side; a click outside, on an entry or Escape closes it. A tag filter (`form.dropdown[data-kind="filter"]`) only filters the list of its own window. The open panel hangs fixed below its button and opens to the bottom right (left edges flush, point 158.2); only without room on the right it turns right-flush, and upwards when there is more room above. In row actions the toggle is a frameless `control-button` instead (A360); the row actions stay visible while its panel is open. Every entry shows a visible hover and keyboard focus; the chosen entry has the marked look (point 158), follows scrolling and resizing, and scrolls when longer than the space.
- **"⋯" menu** – `<x-more-menu><a class="menu-item" href="…" data-window><x-icon name="pencil" /><span>Bearbeiten</span></a>…</x-more-menu>`: entries with icon and text; an entry with `data-window` opens its target as a window on the right. Fits in a window's `actions`. A line `<hr class="menu-separator">` sets entries apart; a destructive entry (Löschen) is `menu-item menu-danger`, red, always last below a separator. Entries never wrap; a menu is as wide as its longest entry. **A module's own ⋯ menu** is not written by the module: `<x-window>` draws it at the right end of the toolbar; the module puts its entries in the slot `menu`. **A351:** the framework's first entry is "Auf Home anheften" (`pin`, `[data-pin-home="<dashboard.pins.store>"]`, `core/window-pin.js`): it posts the window's address (as a path), title and symbol to Home's Schnellzugriff, toasts the answer and emits `dashboard:pinned`; a separator follows when the module has entries. Only the Home window itself (`kind="dashboard"`) and pages without sign-in have no such entry – and with no module entries either, no ⋯ button (A200). A separator with nothing visible below it hides.
- **Dashboard-Baustein (Home, points 176, A349–A353)** – `dashboard/index.blade.php` (`modules/dashboard.js`, `modules/dashboard.css`): one window `kind="dashboard"` (22/60/160rem) with `<ul class="dash-grid" data-dash-grid>` of cards `<li class="card dash-widget is-s|is-m|is-l" data-widget="<type>" data-size>` (`dashboard/_widget.blade.php`, body `dashboard/widgets/<type>.blade.php`). The grid follows the window width (container `win`): one column below 34rem (phones: the widgets stack), two up to 60rem (S/M one column, L both), then six (S 2, M 3, L all). **Edit mode** only via the pencil icon button in the toolbar (`data-dash-edit`, `aria-pressed`, tooltip "Home bearbeiten" / "Bearbeiten beenden"): `.dash.is-editing` shows the "+" dropdown (`data-dash-add`, the widget types not yet shown), each widget's tool line `.dash-tools` (grip `data-dash-grip` – pointer drag or arrow keys, Escape puts back –, name, a Knopfgruppe S/M/L, X) and everything `.dash-edit-only`; every change saves at once (`POST dashboard/layout` with the widgets in order). Outside the edit mode nothing moves. Parts: `<x-empty>` (an empty widget's hint, Leerer Zustand; `.dash-empty` only in the photo field), **"Erste Schritte"** (point 213, F31: `dashboard/_first-steps.blade.php` above the grid – steps that tick themselves from the data via `App\Domain\Dashboard\FirstSteps`, each a `data-window` link to where it is done; the X hides it per person in `user_dashboards.first_steps_hidden_at`; gone by itself once all steps are done), `.dash-tiles` > `.dash-tile` (Schnellzugriff: symbol + title, an app address opens as a window, https in a new tab; X `.dash-tile-x` in edit mode), `.dash-drop` (Ablegen: a big dashed field; files go to `documents.store` without a folder = the Posteingang, the framework's `.is-drop-target` while hovered), `.dash-photo` (the person's own picture, served by an auth route only to its owner). Layout per person and organisation in `user_dashboards` (`App\Domain\Dashboard\DashboardLayout` checks every widget, size and pin). **Pinned notes widgets** (point 233, A395–A397): `DashboardLayout::PINNED` types `note_column` and `note` carry the id in `ref` (`data-ref` on the card), may exist once per id and come only from the pin on the notes board (`home/_pin.blade.php`, `.note-tool.note-pin` with `aria-pressed`, tooltip "An Home anheften" / "Von Home lösen", `modules/notes-pins.js`), never from "+". A column widget lists its notes as coloured rows linking to `notes.index?note=<id>` (the board scrolls there, `.note.is-found`); a note widget shows the text in the note's colour (`.dash-note`), editable in place through `notes.text`. Deleting the column or note takes the widget off every Home (`App\Domain\Dashboard\NotePins::forget`); moving a note keeps it.
- **Menü-Fenster (menu window, point 156, A331)** – `<x-menu-window :title :icon :url :close view="key" display="tiles|list" :entries="[…]">`: an `<x-window>` (kind `menu`) whose body lists entries, each `[href, icon, title, text, badge, count]`: icon, name, short description, red count (`badge badge-alert` with its Badges key, hidden at 0), chevron. Every entry is a `data-window` link, so a click opens the next window on the right (the window system closes the ones right of it and marks the entry as opener row). **Display:** "Liste" (rows, the description small under the name) or "Kacheln" (icon, name, two lines of description, count in the corner; a grid that follows the window width via the container `win`). ## 4. Layout

- **The main menu has no sub-items** (PO, 2026-11-07). Every sub-area, entry and record opens on the right as a window.
- Left: the main menu. Its wall can be dragged: wide = open, narrow = icons only, too narrow = hidden (then a floating menu button). Phones: a drawer.

## 5. Window system

- **Search in the toolbar** – `<x-window search="Placeholder">`: a small search field in the window toolbar with X (close) and magnifier (search) inside; Enter or the magnifier reloads the window body with `?q=…`, the module reads `q`. Optional search panel behind a chevron (slot `searchOptions`, prop `search-params`), see below.
- **Progress dialog** – a dialog without `data-dialog` (not closable) with a `<progress>` and a step line, for long server work (update install).

The general logic of the app (points 22, 24, 40, PO 2026-11-08): **every window is an area of its own** – it scrolls by itself and closes by itself, without touching the others.

**Principle (PO, 2026-11-11, must hold for every module):** every window in the row is **one instance of a module bound to one resource** (folder window = folder module for folder X, detail window = detail module for file Y), like Explorer windows: same code, look and functions per instance, each works on its own inside its column. Several windows of the same module side by side must work – **including the same folder or document twice**: a click always opens a **new** window to the right, never just focuses an existing one. The row is a path/history: a **main-menu choice drops the whole row**; opening something in window N closes everything right of N and opens the new window at N+1.

**Modules (PO, 2026-11-12, points 71, 73):** folder windows, document details, the settings levels and pages, and the **whole notes board** are modules. A module's inner parts (e.g. the notes columns) are plain content, never modules, and never fold. Every module window behaves like a Windows window: **minimise, maximise, close** – nothing else (point 74: no pin; maximise does its job). Windows stay in a row (no free desktop) and are loaded via fetch.

- A link with `data-window` in a window **closes every window right of that window** and opens the new window on the right – always a new instance, also when the same address is open already. Which windows become strips decides the width rules below.
- **Widths like Apple's split view (NSSplitView; points 54, 55, 64, A91–A94).** Every window declares **min, optimal, max** width and a **priority** (`<x-window>` props `min`, `optimal`, `max`, `priority`; defaults per `kind`: `folder` 20/26/96rem prio 1 · `trash`, `mail` 22/30/40rem prio 1 · `notes` 22/40/96rem prio 1 · `dashboard` 22/60/160rem prio 1 · `detail` 30/44/64rem prio 2 · `text` 32/48/72rem prio 2 · others 24/32/48rem prio 1). The row **never scrolls sideways**: the windows always share exactly the width there is.
- **Space follows attention (point 199).** What a window *needs* comes from its **content**, not its module type: `<x-window fit="…" content="…">` (also on its `.win-body`, so a body reload – search, view switch – brings the new hint and the row lays out again). `fit`: `narrow` (a few rows, e.g. only folders: 22rem, **never grows past it** except as the last window), `medium` (a detail: 44rem), `wide` (a document list with date, size, tags: 56rem), `full` (tiles, gallery, calendar: 64rem, grows up to max) or a length; always kept within the module's min/max. Without `fit` the need is the optimal width. `content` names what is shown (`folders`, `documents`, `gallery`, `detail`, `booking` …) for the remembered hand width. Reference: `documents/index.blade.php` (folder rows only → narrow, list/details/timeline → wide, tiles/calendar → full).
  - **A window opens beside another** (or a strip is opened again): every other window goes back to **at most what it needs**, the new one gets the rest (it grows first, up to its max; the last wide window takes what is left). Example: left the narrow folder list, right the wide documents list.
  - **Room runs out:** the others shrink to their min, lowest priority first, **among equals from the left**; then the **leftmost** (lowest priority) becomes a strip – the new window keeps at least its need (preferred width, at most its optimal) and stays large.
  - **A window closes:** the others keep their widths and the last wide window takes the room back.
- Apart from that, a window keeps its width from one layout to the next; only the difference is shared out (close, minimise, browser/menu resize):
  - too little room → windows shrink towards their min, **lowest priority first, among equals from the left**; still too little → the lowest-priority window becomes a **strip** – never the newest or the one just opened/opened again (that one keeps its width, at most its preferred, while the others make room);
  - more room → a strip the layout made opens again as soon as the wide windows **at their min** leave room for its **min + 4rem** (A96: hysteresis, almost where it collapsed; a window that keeps its width or was sized by hand counts with that width, at most its preferred); then windows grow back to their preferred width, then to their max; the rest goes to the last wide window;
  - a click on a strip opens it again at its preferred width; the others make room by the same rules.
- **Dragging an edge (A91–A94):** computed from the state at drag start plus the whole distance, so the edge stays under the pointer; windows left of it never move. Wider: the windows right of it give way, lowest priority first (among equals from the left), each down to its min; then the edge stops, and **3rem** further the lowest-priority one snaps to a strip (never the newest). Dragging back until its min fits snaps it (and strips the layout made on the right) open again at its min – a 3rem band in between. Narrower: the right neighbour takes the room. During a drag nothing else lays out; on release the width is remembered per **window kind + content kind** (see below). The last window has no edge. Each window lies above the next one (descending `z-index`), so the edge's right half over the neighbour stays grabbable (A95).
- **Measuring jumps (point 63 / A90):** `?debug=layout` switches a measurement on for the tab (`?debug=off` ends it): user actions, window size changes and strips, layout shifts and elements gone and back within 300 ms; a small panel bottom right copies the log ("Messung kopieren") or empties it.
- **Strip:** the unfold arrow **›** (`chevron-right`) on top on the head line opens it again, then icon and title turned by 90°, the small X.
- **Head (like Windows, points 42, 70, 72, A116–A124):** icon, title (always visible, ellipsis), then on the right the three **window controls**, always in this order and look (frameless `control-button`s, 36 px): **minimise** ‹ (`chevron-left`, "Minimieren"), **maximise** (`window-maximise`: four small chevrons pointing out to the corners, "Maximieren"; while maximised `window-restore`: four chevrons pointing in, "Wiederherstellen", `aria-pressed="true"`; own SVGs in Tabler style with the stroke of ‹; on hover they pulse outward / inward, with "reduce motion" only the colour changes – points 87, A179, A180), **close** X (`x`, only with a `close` target). The line of the settings column heads.
  - Minimise makes the window a strip and it **stays** one until it is clicked.
  - Maximise: this module fills the row, **all others become strips** (`data-maxed` on the window, `is-maxed` on the row, no drag edges). A second click restores every window's strip state and width from before. Opening a window, clicking a strip, minimising or closing ends the maximised state; a reload keeps it.
  - **Phones (< 64rem):** only the back arrow (left) and X; no minimise, no maximise.
- **Toolbar (point 41):** the search field, the module's buttons (`actions`, small 36 px icon buttons) and, at the right end, the module's ⋯ menu stand in a row below the head. It follows **the window's own width** (container queries on `.win-frame`, container `win`), not the screen: wide = one row (search left, buttons right); below 44rem the search takes its own row; below 28rem the window is **narrow**: elements with `win-wide-only` hide, elements with `win-narrow-only` show. Use that to turn a button group into one dropdown button and extra buttons into entries of the module's ⋯ menu (slot `menu`) (reference: the view switcher and "Neues Dokument"/"Neuer Ordner" in `documents/index.blade.php`). The toolbar wraps before anything is cut at the window edge.
- The window just opened or opened again scrolls into view.
- **Width by hand (points 44, 54.5):** every wide window has a drag edge on its right (`.win-edge`, built by `<x-window>` like the back arrow `.win-back` on narrow screens; same look as the wall right of the menu): drag or arrow keys (Shift = bigger steps) set its width by the drag rules above – also below its min (at least 12rem); double-click goes back to **automatic** (the content's need). Point 199: the width is remembered per **window kind + content kind** (`DocHamster.windowHand`, `localStorage` `dh-win-hands`, key e.g. `folder:folders` = the folder overview) and is the preferred width of every such window from then on – also after a reload; a narrow window sized by hand may then grow like any other. Without one the content hint decides. Not on phones (phones show one window at a time, unchanged).
- **Window state lives in its address (point 52):** a module setting that belongs to one window (e.g. the list view `?view=timeline`) is a query field of the window URL, so each instance keeps its own and reload keeps it; changing it reloads only that window (`DocHamster.reloadWindow(win, url, '.win-frame')`). A window without it starts with the person's last choice.
- The **X** in a window's head closes just that window; the small X on a strip removes it from the history. If no wide window is left, the nearest strip opens. **Every module has an X** (point 112), the first window too; closing the last one leaves the area empty, without a hint (A219) – the main menu opens the next.
- **Opener row (Öffner-Zeile, point 141, A306, A307):** the row, tile or link in window N whose click opened window N+1 stays marked while N+1 is open – the marked-row look (point 155: white surface, shadow, orange symbol; a `tr` gets the white surface on its cells). The window system does it for every module: the row is the link's closest `[data-window-row]`, `li` or `tr`, else the link itself (`a[data-window]` in the head, toolbar, search panel or a menu marks nothing); give a module's row element `data-window-row` when it is no `li`/`tr`. Each window remembers its opener (`data-window-from` = window id, `data-window-opener` = link address, kept in the tab's history), so the mark moves with the next click, goes with the child, and comes back after a body reload (search, view switch, `DocHamster.reloadWindow`) or a page load – found again by the link address (exact, else same path with the most equal query fields). The mark stays for good (point 162): the hover does not change it and it wins over a coloured row and the open-document tint. When both windows stand next to each other on a wide screen, the opener window shows a short orange line on its right edge at the row's height (`has-opener-line`, `--opener-y`), like the Finder's column view – the row itself has no notch any more (point 162; windows.js still sets `is-linked`, no CSS uses it); the line hides when the row is scrolled out of view, a window is a strip, or the windows are not adjacent. Modules do nothing.
- The **active** window is the one opened last or clicked into; the browser address and the title follow it. Browser back opens the window of the entry before (the entry names the window, so two windows with one address work). A reload keeps the history of this tab with which windows were minimised or maximised (`sessionStorage`); windows not loaded yet load when they are shown. A link in the main menu drops that history.
- Changes glide (view transitions where the browser has them; none with "reduce motion").
- **Vorladen and the window cache (point 164.8, A342; `core/window-cache.js`):** windows.js loads every window through `DocHamster.windowCache.take(url)`. A window kept in memory opens at once and refreshes quietly afterwards (the server answers 304 while unchanged; new content replaces `.win-frame`/`.win-body` only while the person hasn't touched the window). Filled by hover intent (80 ms) or touch on `a[data-window]`, the small windows (menu windows, Dokumente, Bank) once per tab session, the window this person usually opens next (learned per user), and with "Stark" the window links of the active window while idle. Any non-GET fetch or posted form drops the cache – a module needs to do nothing. Prefetch requests carry `X-DocHamster-Prefetch: 1`: **a GET with a side effect (mark as seen, opened) must skip it when `App\Http\Speed\Prefetch::is()`**. Option: Einstellungen → Geschwindigkeit → Vorladen (`<body data-prefetch>`); data saver, 2g or a slow server → hover intent only. Main-menu links: browser prefetch on hover (speculation rules); a link that must not be prefetched gets `data-no-prefetch`.
- **On its way (point 164.8d):** the clicked row gets `is-pressed` at once; after 150 ms a thin orange bar runs along the top of the row of windows (`.windows.is-loading`).
- Phones: one window at a time, with a back arrow in its head (opens the window left of it).
- Without JavaScript every link is a normal page; the page shows its windows side by side.

### How a module uses it

**Page:** wrap the windows of a page in `<div class="windows" data-windows>` and set `@section('main_class', 'page-windows')`. The page's **last** window is the page itself.

```blade
@section('main_class', 'page-windows')
@section('content')
    <div class="windows" data-windows>
        <x-window :title="__('documents.title')" icon="receipt" :url="route('documents.index')">
            <x-slot:actions>…filter, view…</x-slot:actions>
            …the list…
        </x-window>
        @if ($open)
            <x-window :title="$open->title" icon="file-text" :url="route('documents.show', $open->id)" :close="route('documents.index')">
                …the receipt…
            </x-window>
        @endif
    </div>
@endsection
```

**Links that open a window:** `<a href="…" data-window>`. The framework loads the target in the background with the header `X-DocHamster-Window: 1`; the layout then returns only the content (no menu, no frame), and the framework takes the page's last `section[data-window]`. Every click loads a new instance, even for an address that is open already. Modules need no extra route or controller code.

**`<x-window>` props:** `title`, `icon` (Tabler name), `url` (this window's address; default the current one), `close` (where the X leads without JavaScript; always set, point 112), `upload` (where an upload belongs while this window is active, as form fields, e.g. `upload="folder=01H…"`), `min`, `optimal`, `max` (widths for the automatic layout, e.g. `min="36rem"`) and `priority` (higher = becomes a strip later), defaults per `kind` (see the width rules above), `fit` and `content` (point 199: the width the content needs and what it shows, see "Space follows attention"), `kind` (module type, e.g. `folder`, `detail`; default the route name), `search` (placeholder of a search field in the toolbar, see below), `search-live`, `search-params` and slot `searchOptions` (search panel, see below), slot `actions` (buttons in the toolbar), slot `menu` (the module's entries of its ⋯ menu, below the framework's "Auf Home anheften", A351), extra classes via `class="…"`. Every window has the toolbar row (at least the ⋯ menu).

**Notes module (points 71, 73, A121, A122, A200):** it can be open several times; the main menu "Notizen" (`notes.index`, /notes, point 175) opens it as the first module; "Home" is the dashboard (Dashboard-Baustein). The ⋯ menus no longer carry a "Notizen daneben öffnen" entry.

**Search field (A104, points 102–106):** `<x-window search="Ordner und Belege suchen">` puts a small search field (`input-small`) in the toolbar, a Field with symbol: **X** (`data-window-search-clear`, shown while a search is set) and a **magnifier** submit button inside; in a window below 44rem it gets its own row. **Enter or the magnifier** searches: the framework loads the window's address with `?q=…` (same `X-DocHamster-Window: 1` fetch as window links) and swaps **only the body** (`.win-body`), so the field keeps focus and caret; the address follows with `replaceState`, reload and the stored history keep `q`. A new search drops `page`. `search-live` (prop `searchLive`) makes typing search too (300 ms pause); default off (A203). The X or Escape in the field **closes the search**: it empties the field and the panel and loads without `q` and the panel's parameters, so the window's own view (e.g. `?view=…`) comes back. Any other element with `data-window-search-clear` inside the window does the same (e.g. an X link in the head of a result list; give it the address without the search as `href` for no-JS). Every window has its own search; the new body gets `window:open`.
**Search panel (points 102, 135, 187, A282-A285):** slot `searchOptions` adds a chevron button beside the field that opens a panel **inside the same form** with the module's fields. **Look (187.7):** one card right under the search row (`.win-search-area`: the window's side padding, white `--bg`, thin border, 12 px corners); while it is open the search takes the toolbar's last row on its own and the chevron becomes the card's **tab** – same background and border, no bottom border, the chevron turned up, a small concave 8 px curve on its left where it meets the card's top edge (`::before`), the card's top-right corner square under it; closed it is a normal icon button (orange frame while a filter is set). **Layout (187.3):** on top the rows that are **always visible** (`.search-top`, `.search-line`s – e.g. "Suchen in:" as small toggle chips `.chips.chips-small` and "Wo:" as an Umschalter); below them the module's sections as **compact foldable cards** in **one column** – never a two-column grid (`.search-sections`, `<x-fold-card compact :remember="false">`), **folded at first, open by themselves when a filter in them is set**, each head with a summary of what is set (e.g. "Zeitraum: Dieser Monat · Belegdatum", "Tags: 2 gewählt"). Inside a section the lines are `.search-line` (label column + control, small fields, A284) and choices are **Umschalter** ("Alle | Ja | Nein", "Alle | PDF | Bild" – never "egal" selects or radios). **Narrow (187.6, container query on the window, < 30rem):** labels stand above their control, Umschalter fill the width and become a select only when they still do not fit (never wrap mid-group), tags wrap as chips, never a horizontal scroll; on phones the toolbar keeps the floating menu button's room on the left. **Footer (187.4):** inside the card, at its bottom while it scrolls (`.win-search-actions`, from `<x-window>`): a quiet link "Zurücksetzen" on the left, the normal button "Suchen" (magnifier + text) on the right; Enter in any field of the panel searches. Name the fields in `search-params="in[] all"`: they are sent with `q` (empty ones are dropped from the address, and so are ticks that all stand as they start – `data-default` on the checkboxes that start ticked), kept out of the form's hidden fields, dropped when the search is closed, and the chevron is marked (`is-active`) while one is set. After a reset or a removed chip the framework calls `DocHamster.syncChoices(area)` and emits `search:reset` (area) so the module can update its summaries. Reference: `documents/index.blade.php` + `modules/documents-search.js` ("Suchen in" Name | Erkannter Text | Notiz | Tags | Eigenschaften as `in[]`, default Name + Erkannter Text, at least one stays on, the old `ocr=1` still adds the recognised text; period Dieser Monat | Letzter Monat | Dieses Jahr | Letztes Jahr | Eigener – date fields only for "Eigener"; property filters: "+ Filter hinzufügen" picks a property and shows one `.search-prop` row with the input of its type, "Alle | hat Wert | fehlt" and an X); the bank account window uses the same panel. **What is found is the module's job:** its controller reads `q` and its own parameters (and must render the search field's window again with the filtered body). Without JavaScript the field is a normal GET form (the panel needs JavaScript to open).
- **Search button rule (A305, 187.4):** a button that runs a search shows the **magnifier icon** (`search`) with the tooltip and label "Suchen" – never the word "Filtern". Only the search panel's footer has the magnifier **with** the text "Suchen" (a normal button, the panel's main action). This holds for the window search field, the search panel and filter forms on pages (e.g. Einstellungen → Log).

**Uploads:** the main menu has no upload button any more (point 180); "Hochladen" sits in the Posteingang's head (a file button, point 182) and files dropped go where they are dropped (see "Upload by drop"). Which fields a window sets and what the server does with them is up to the module.

**JavaScript of a module:** windows arrive after the page has loaded, so "run on DOMContentLoaded" is not enough. Register instead:

```js
DocHamster.on('window:open', root => {
    root.querySelectorAll('[data-my-thing]').forEach(setUp);
});
DocHamster.on('window:close', root => { /* clean up timers etc. */ });
```

`window:open` runs for every window of the first page and for each window loaded later (`root` is that window; on pages without windows it is `document`). Prefer delegated listeners on `document` where you can.

**IDs (multi-instance):** a window can be open twice – also with the **same** record. Write ids, `for`, `form`, `aria-*` references and dialog names as usual (with the record's id where it helps reading); the framework gives every id in a window a per-window suffix and rewrites the references in that window (`for`, `form`, `list`, `aria-labelledby/-describedby/-controls/…`, `href="#…"`, `data-copy`, `data-focus`, `data-dialog`/`data-dialog-open`). A dialog opener finds its dialog in its own window first. In module JavaScript never look up window content with `document.getElementById` or `document.querySelector` – start from the window (`root` of `window:open`, or `el.closest('section[data-window]')`) and keep state per element (`WeakMap`), not per page.

### Erweiterungen

Einstellungen → Erweiterungen (`settings/extensions`, point 173, `ExtensionController`, `resources/views/settings/extensions.blade.php`) lists everything optional on one page: name, short description, size, installed/version and the buttons **Installieren** (download), **Aktualisieren** (cloud-download), **Entfernen** (trash, with a confirm dialog) – icon + text – and for an installed data pack a pause/play icon button to switch it off without deleting it.

- **Only the fixed catalogue** `App\Infrastructure\Extensions\Catalogue` (a PHP class, not config): every file with pinned URL, SHA-256 and size. Never an address from a request.
- **Data pack** (`Extension::DATA`): files only, no code, into `storage/app/<dir>/`. The download is the net job `App\Jobs\Net\InstallExtension` (D-020, `SetUpOcr::fetcher()`), then `Extensions::verify()` checks size + SHA-256 again. State: `storage/app/extensions.json` (`installed.<key>`: version, files, enabled, at). The feature reads its packs itself: `Extensions::enabled('<group>')`.
- **Module with code** (`Extension::MODULE`): one zip (pinned SHA-256 + size), planned: unpacked to `modules/<key>`, `module.json` checked by `ModuleManifest::check()` (key, version, provider class, migrations path), provider registered, migrations run; Entfernen unregisters and keeps the data unless asked. Not installable yet: such entries show the pill "kommt später" and have no buttons.
- **OCR languages (point 171)**: group `ocr`, tessdata_fast 4.1.0 into `storage/app/ocr/tessdata`. The core ships only deu + eng. OCR always runs with all installed and enabled languages together (`LocalOcr::languages()`, e.g. `deu+eng+ell`) on the server (app tesseract; a system tesseract gets `--tessdata-dir` / `TESSDATA_PREFIX` when the app dir has every language) and in the browser (tesseract.js loads `ocr/lang/<code>.traineddata`). A document can get its own language under "Text neu erkennen" (A345, `documents.ocr_langs`). A346: the page offers to re-read documents whose text looks broken (`OcrTextQuality`).
- **Requires / bundles (point 172)**: an entry's `requires` (catalogue keys) are installed first and marked `auto` in the state; removing an entry also removes its `auto` requires nothing else needs. A bundle is an entry without own files (only `requires`): no on/off button. `meta.hidden = 1` keeps an entry off the page (it only comes along with others).
- **Translation (point 172)**: group `translate`, Mozilla's Firefox Translations (Bergamot, MPL-2.0) from Firefox Remote Settings only – the set Firefox ESR 140 runs: runtime `translate-engine` (bergamot-translator wasm 2.0, hidden, required by every pair; its JS glue of the same Firefox revision is `public/vendor/bergamot/`), pairs `translate-<from>-<to>` (model + lex + vocab, meta `from`/`to`/role → file name) into `storage/app/translate/<pair>`, bundle `translate-el-de` = el-en + en-de (no direct model; over English). The browser translates (`public/js/translate-worker.js` in a Web Worker, `modules/translate.js`), files come from `translate/files/{key}/{name}`; `Translations` picks the source language and the route (direct or English pivot). Result in `document_translations`, one per target language, searched with "Auch im erkannten Text".
- **Adding a pack**: one more catalogue group or entry, its names in `lang/*/extensions.php`, and the feature that reads `Extensions::enabled('<group>')`.
