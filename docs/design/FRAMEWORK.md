# docHamster UI framework

The one source for how docHamster looks and behaves. Every page and every module (Belege, Notizen, Ordner, Bank, Einstellungen, later the bank modules from their own repos) is built **only** from the building blocks below. Live samples: `/design/styleguide.html` (section "Framework").

Rules for agents (also in `AGENTS.md`):

1. Read this file before you build UI.
2. Use only these classes and components. No own colours, shadows, button looks or column/window logic in a module.
3. A new building block is made on the long-running branch `lead/framework`, documented here first, then used.
4. Plain CSS and JS without a build step (D-004), split by topic (A216): `public/css/core/*.css` and `public/js/core/*.js` = the framework (base, layout, forms, buttons, menus, lists, windows, menu windows, dialogs, tooltips …), `public/css/modules/*.css` and `public/js/modules/*.js` = one file per module (documents, notes, ocr, updates …). The load order is `config/assets.php` (the styleguide links the same CSS list); a new file goes there. UI strings via `lang/`.

## 1. Colours and surfaces

Tokens on `:root` in `css/core/base.css`, light and dark follow the system setting.

| Token | Use |
|-------|-----|
| `--primary` `#ff7622` | Main buttons, active marks, icons in heads. **Filled orange is only ever a button.** |
| `--primary-hover` | Main button on hover |
| `--primary-ink` | Orange text and links on the page background |
| `--secondary` | The dark block behind logo and menu button |
| `--bg`, `--surface` | Page and slightly darker surfaces (menu, strips, rows) |
| `--text`, `--muted`, `--border` | Text, quieter text, lines |
| `--danger`, `--ok`, `--error` | Delete buttons, success, errors |
| `--shadow` | One soft dark shadow for everything that floats: tooltips, menus, dialogs, toasts |
| `--button-shadow` | The shadow under buttons |

Sticky notes keep their own 20 colours (`.note-*`); they are not app colours.

## 2. Buttons

Every `<button>` and `.button` is a button by default. Do not reuse its look for anything else.

| Kind | Markup | When |
|------|--------|------|
| Main | `<button>` | The one main action of an area |
| Side | `<button class="button-quiet">` | Cancel and side actions; outlined, no fill |
| Delete | `<button class="button-danger">` | Delete only |
| Small | add `button-small` | 40 px instead of 48 px, e.g. in list rows |
| Icon | `<button class="icon-button" aria-label="…" data-tooltip="…">` | Square, icon only, always with tooltip |
| Group | `<div class="button-group" role="group" aria-label="…">` around buttons | Buttons side by side (e.g. view choice); rounded only outside, the chosen one `aria-pressed="true"` |
| Control | `<button type="button" class="control-button" aria-label="…" data-tooltip="…">` | Window controls only (minimise ‹ – one term, A218 –, unfold ›, maximise, close): **no frame**, icon in text colour, orange on hover; 36 px in window heads. The menu arrow is its 48 px flavour (points 70, A116) |

48 px high (small 40 px), 10 px corners (icon buttons too, link or button), semi-bold, no letter spacing, light shadow that presses in on click, orange focus ring for the keyboard, faded when disabled. A link stays underlined text and never looks like a button.

**Cursor (A192):** everything clickable shows the hand – one central rule in `css/core/buttons.css` (`:where(…)`, zero specificity): buttons, `.control-button`, icon buttons, row actions, menu entries, links (also whole rows), `summary`, tabs, strips, colour swatches, icon choices, chips, checkbox/radio labels and `select`. Drag edges show `col-resize`, things that move `grab`; disabled things `not-allowed`. Don't set `cursor: pointer` per module.

## 3. Form fields, cards, lists, toasts, dialogs

- **Form field** – label **above** the field (orange, semi-bold), a quiet thin frame, 8 px corners, 48 px high; while typing an orange frame with a soft orange ring; an error gives a thin red frame. The same look for text, password, search, date, number, `select` and `textarea` (grows with its text). Checkboxes, radios, colour and range keep their own look. Saved logins (autofill) look like typed text.
  ```html
  <div class="field">
      <label for="username">Benutzername</label>
      <input id="username" name="username" autocomplete="username">
      <p class="field-hint">Optional: a hint below the field.</p>
  </div>
  ```
  An error: `class="field has-error"` (red frame, red hint) or `aria-invalid="true"` on the field. Older forms with the label right before or around the field are drawn the same way; new code uses `.field`.
- **Small field** – `class="input-small"` on an `input` or `select`: 40 px high like small buttons, for tight spots (a search above a list, a field in a row). No label above, a placeholder says what goes in (and `aria-label`). Every `type="search"` field is small by itself.
- **Frame field** – `<fieldset><legend>Tags</legend>…</fieldset>` for a group (tags, checkboxes, colours): no browser frame, the legend stands above like a field's label.

- **Card** – a framed block with a head: `<section class="card"><h2 class="card-head"><x-icon name="…" />Title <form class="card-action">…</form></h2> … </section>`. Text in a card: `.card-text` (readable line length), small print `.card-note`.
- **Card head with action (task 110)** – at most one `form.card-action` at the right end of the head: an icon button (`icon-button`, tooltip) or, for the card's main action, a small button with symbol and text (`<button class="button-small"><x-icon name="refresh" />Update</button>`). Its symbols keep the button's colour. With `data-ajax` the button is busy (`is-busy`: disabled, its symbol spins) until the answer is in.
- **Karte, klappbar (foldable card, point 125, A260/A261)** – `<x-fold-card fold="ocr.mode" :title="…" icon="…" folded summary="App-eigen" summary-tone="ok">…</x-fold-card>` (slot `action` for a `form.card-action`): a card whose head ends in a chevron (`control-button card-fold-button`, `aria-expanded`, tooltip "Aufklappen"/"Zuklappen"; **rule (point 131): the chevron points down while folded = "Aufklappen" and up while open = "Zuklappen"**, every foldable section in the app follows it) that hides the body (`.card-body[hidden]`, the card gets `is-folded`). A folded card shows a short **summary** in its head (`.card-summary`, `is-ok` green check / `is-warning` warning triangle, or `summary-icon`), e.g. "App-eigen ✓", "kein Cronjob ⚠". The page sets the start state (`folded`); what a person folds is remembered **per card id** (`fold="<page>.<card>"`) in the plain cookie `dh_folds` (`core/card-fold.js`, delegated) and the **server draws that state** (`App\Http\CardFolds`), so nothing jumps on load – also in windows loaded later. `DocHamster.foldCard(card, folded)` folds from code; every toggle emits `card:fold { card, folded }`. Use it where a page has several cards and some are rarely needed; a page with one card keeps a plain card. **Compact variant (point 135):** `<x-fold-card compact …>` (`card-fold is-compact`) for sections inside a panel, e.g. the search panel: no frame, a line below, a small head; the summary shows open and folded (empty = hidden, a module may update `[data-card-summary] > span` live). `:remember="false"` (`data-card-fold-forget`) draws the page's state every time and remembers nothing – e.g. "folded unless a filter in it is set".
- **Knopfgruppe als Auswahl (button group as a choice, point 135, A283/A284)** – instead of radios or a select with "egal": `<span class="button-choice" data-choice><input type="hidden" name="match" value=""><span class="button-group" role="group" aria-label="…">` with small quiet buttons `data-value="…"` (`aria-pressed`); the "Alle" / default option is `data-value=""` and comes first. A click sets the hidden field and `aria-pressed` and sends `change` from the field (`core/button-choice.js`, delegated); `data-choice-toggle` lets a second click on the pressed button set it back to "". After code changed the fields, `DocHamster.syncChoices(root)` makes the buttons follow. Blade in the documents search: `documents/_search-choice.blade.php`.
- **List with rows** – `<ul class="pick-list">` with `<li class="pick-row is-static">` (icon, `<span><strong>…</strong><small>…</small></span>`, optional `pill` labels and a small button on the right; the text part takes the free width, so labels and button line up at the right edge). An empty or not yet loaded list shows `<li class="list-empty">Keine Einträge</li>`; an error `list-empty list-error`. A row that opens something has its link around the title (`<strong><a href="…" data-window>Name</a></strong>`): **the whole row is the click area**, nothing is underlined or orange, hover darkens the row, the keyboard shows an orange frame around it. Buttons in the row stay clickable on their own.
- **Links** – never underlined, except inside running text (`p`, `.card-text`, hints) – and even there only in rare cases. Lists, heads, menus and tabs never show a link look.
- **Ajax into a card** – `<form data-ajax="#target">`: sends in the background, the controller answers JSON `{html}` with a partial, which replaces `#target`. Without JavaScript the form posts as usual.
- **Marked row (task 110)** – one look for "this one is the current / chosen one": a raised white surface (`--mark-surface`, dark mode a lighter surface) with a light shadow (`--mark-shadow`) and the orange symbol – no bar, no border, no bold text (point 155, variant A3). Used by the current menu entry (`nav-item[aria-current="page"]`), a checked menu entry, a picked choice row (`pick-row:has(input:checked)`) and a marked list row `<li class="pick-row is-static is-marked">` (e.g. the installed version). Not for multi-select (that is `.is-selected`, orange tint). The same look marks the **opener row** of a window (`.is-opener`, set by the window system, § 5).
- **Pill (task 110)** – `<span class="pill">`: the one small round label for states and counts, not clickable. Quiet framed by default ("Vorschau", OCR state, the count in a tab); `pill-ok` green ("installiert"), `pill-new` orange tint ("verfügbar"; also the count of the active tab). Replaces `.tag-outline` and `.tab-count`. `pill-warning` orange and `pill-error` red mark the kind of a log entry (point 115).
- **Errors are logged (point 115)** – server errors and browser errors (uncaught errors, failed promises, a module that throws inside `DocHamster.emit`) land in Einstellungen → Log, logbook "Allgemein", level error (`core/error-report.js`, at most five per page). The event bus never lets one module break another or the window system.
- **Count badge** – `<span class="badge">3</span>`: a round number. Orange; on an `icon-button` it sits on the top right corner (filter count). `badge badge-alert` red, for new things in the main menu (A8–A11). Replaces `.nav-badge`.
- **Toast** – `<div class="toast" role="status" data-toast>…</div>`: top right (on phones at the bottom), closes itself after 5 s.
- **Dialog** – `<div class="dialog-backdrop" data-dialog="name" hidden><div class="dialog" role="dialog" aria-modal="true">…</div></div>`, opened by any `[data-dialog-open="name"]` (also in windows loaded later). `data-dialog-title` on the opener sets `[data-dialog-heading]`. Close: `[data-dialog-close]`, the backdrop, Escape. Names must be unique on the page – put the record's id in them. Asking for the password happens only in a dialog.
- **Top layer (point 53)** – while shown, dialogs, dropdown panels, toasts and the tooltip lie in the browser's top layer above every window (app.js lifts them as `popover="manual"` when `hidden` goes away): never cut off at a window edge, a dialog's backdrop greys the whole app, later shown = on top. They stay in their place in the DOM, so forms, `closest('section[data-window]')` and per-window names keep working. Just toggle `hidden`; never set `popover` yourself.
- **Dropdown** – `<div class="dropdown"><button type="button" class="icon-button" aria-expanded="false">…</button><div class="dropdown-panel" hidden>…</div></div>`. Works in every window, also in windows loaded later and several side by side; a click outside, on an entry or Escape closes it. A tag filter (`form.dropdown[data-kind="filter"]`) only filters the list of its own window. The open panel hangs fixed below its button and opens to the bottom right (left edges flush, point 158.2); only without room on the right it turns right-flush, and upwards when there is more room above. Every entry shows a visible hover and keyboard focus; the chosen entry has the marked look (point 158), follows scrolling and resizing, and scrolls when longer than the space.
- **"⋯" menu** – `<x-more-menu><a class="menu-item" href="…" data-window><x-icon name="pencil" /><span>Bearbeiten</span></a>…</x-more-menu>`: entries with icon and text; an entry with `data-window` opens its target as a window on the right. Fits in a window's `actions`. A line `<hr class="menu-separator">` sets entries apart; a destructive entry (Löschen) is `menu-item menu-danger`, red, always last below a separator. Entries never wrap; a menu is as wide as its longest entry. **A module's own ⋯ menu** is not written by the module: `<x-window>` draws it at the right end of the toolbar; the module puts its entries in the slot `menu`. A window whose module has no entries shows no ⋯ button (A200). A separator with nothing visible below it hides.
- **Menü-Fenster (menu window, point 156, A331)** – `<x-menu-window :title :icon :url :close view="key" display="tiles|list" :entries="[…]">`: an `<x-window>` (kind `menu`) whose body lists entries, each `[href, icon, title, text, badge, count]`: icon, name, short description, red count (`badge badge-alert` with its Badges key, hidden at 0), chevron. Every entry is a `data-window` link, so a click opens the next window on the right (the window system closes the ones right of it and marks the entry as opener row). **Display:** "Liste" (rows, the description small under the name) or "Kacheln" (icon, name, two lines of description, count in the corner; a grid that follows the window width via the container `win`). Below 13rem window width only the icons stay (count on the icon, the name as tooltip); as a strip it is a normal window strip. A button group in the toolbar (list | layout-grid) switches the display of **that** window; the choice is remembered per `view` key in the cookie `dh_menu_views` (`App\Http\MenuViews`, like `CardFolds`), the module sets the default (`display`). Widths: tiles 16/36/56rem, list 12/22/28rem, priority 1. Optional slot below the entries. CSS `core/menu-window.css`, JS `core/menu-window.js`. Reference: Einstellungen (§ 5, Reference module).
- **Column menu ⋮ (points 65–67)** – a column inside a module (e.g. a notes column) puts all its actions into `<x-more-menu class="kanban-menu" icon="dots-vertical" label="Spalte">` at the right of its head – no loose buttons below or beside the column. The button shows only while the column is hovered or the menu has focus or is open; on touch devices (`hover: none`) always. Order: add, rename (`data-focus="<edit-in-place id>"` starts click-to-edit), colour dialogs (`<x-color-picker>`), move left/right (`disabled` at the ends; `.menu-item:disabled` is greyed), a `.dropdown-title` group of `role="menuitemradio"` entries (sorting), bulk actions, and the red delete entry last. Column colour: class `has-color` + `c-rrggbb` tints the column (no inline styles).
- **Click-to-edit** – `<x-edit-in-place name="note" :action="route(…)" :value="…" multiline placeholder="…" label="…" />`: shows plain text with a quiet hover frame (grey placeholder when empty); click, or Tab + Enter, turns it into a field of the same size; blur or Ctrl+Enter saves (JSON POST, toast "Gespeichert."), Esc restores. A refused value (422) shows the server's `message` in the error toast; after a save the framework emits `DocHamster.on('edit-in-place:saved', ({ box, json }) => …)`. Sticky notes are the model.
- **Sortable list** – (folder rows use the drag and drop above instead; they have no grip, point 82) `<ul class="pick-list" data-sortable>` with rows `<li class="pick-row is-static" data-id="…"><button type="button" class="pick-handle" aria-label="Verschieben"><x-icon name="grip-vertical" /></button>…</li>`. The **whole row** is the grip: with the mouse it lifts after a few pixels, with a finger after a short hold (a quick swipe still scrolls; the handle lifts at once). The row hangs on the pointer, a dashed placeholder keeps its old place (nothing jumps), an orange bar shows where it lands, near the edge the list scrolls along; on release it glides to the bar, Escape puts it back. A short click still opens the row. Keyboard on the handle: Space picks up, arrow keys move, Space drops, Escape puts back. Afterwards `DocHamster.on('list:sorted', ({ list, ids }) => …)` gets the list and the row ids in their new order; **the module saves**.
- **Row symbol (points 81, A144–A146)** – `<span class="row-icon"><x-icon … /></span>` as a row's first child: a fixed 38 px slot, so the names of all rows line up. app.js measures each symbol's own box (`getBBox`, once per symbol), sets it as a tight `viewBox` and scales the symbol to fill the slot – as tall as the two text lines (38 px) – with `vector-effect: non-scaling-stroke`, so the stroke stays 2 px. Without JavaScript it keeps its normal 24 px. Always orange (`--primary`); on a coloured row see below. (The old icon tile is gone.)
- **Inhaltszähler (content count, point 161 / F5 variant D)** – `<x-row-stats :folders="6" :documents="3" :total="50" />` as a row's second line (instead of the `small`): "6 [folder] · 3 [document] (50 [document] insgesamt)" = direct subfolders · own documents (all documents of the branch). Small inline symbols; each part has its words ("6 Ordner", "3 Dokumente", "50 Dokumente insgesamt") as tooltip and as screen-reader text. Zero parts are left out, the bracket shows only when the total differs from the own count, "Leer" only when there is nothing at all. The counts come from one grouped query for all folders of the window plus `Folder::counts()` over the tree (no N+1). Folder rows and tiles use it; the Papierkorb keeps its own count.
- **Listeneintrag (list entry, point 163)** – **one** row building block for every clickable entry: main menu `.nav-item`, dropdown and "⋯" entries `.menu-item`, menu-window entries `.menu-entry` (also the Einstellungen), window list rows `.pick-row` and `.view-list li`, and `.list-entry` for anything new. The flavours keep their class names (layout, icon size); their states are defined **once** in `core/lists.css` – never per module: **rest** no fill (in a filled list, pick rows, the row's surface: `--surface`, a coloured row its colour); **hover** one colour on every surface, the text colour at 7 % laid over the fill (`--row-tint` as a background image, so it never fights a fill; only entries that do something hover; a module row that needs a hover uses `background-image: linear-gradient(var(--row-tint), var(--row-tint))`); **focus-visible** a 2 px orange ring inside; **marked** the point-155 look (below), the hover does not change it; **disabled** (`:disabled`, `aria-disabled="true"`, `.is-disabled`) faded, no hover; **sizes** normal at least 48 px high with .85rem side padding, compact (`.is-compact`, `.view-list` rows) 36 px with .35rem .6rem. Rounded corners `--row-radius` (8 px). Styleguide: "Listeneintrag".
- **Properties module ("Eigenschaften", A191–A194)** – a module that edits one record's properties has **no save button**: `<form method="post" action="…" data-autosave>`. Every choice saves the moment it changes – `select`, radios (colour, symbol), checkboxes, the own colour (picker closed or a complete `#rrggbb`) – as a JSON POST of the whole form; the answer's `message` is the toast ("Gespeichert."). A **text field** saves only on purpose: it sits in a `.field-addon` with a ✓ button `data-field-save` (`hidden` at first); the ✓ shows as soon as the value differs from the saved one, **Enter or ✓ saves**, then it hides again; leaving the field keeps the typed text and the ✓; **Escape** restores the saved value. Until then other saves send that field's saved value. A refused save (422) shows the error toast and a red field frame. After a save the framework emits `DocHamster.on('properties:saved', ({ form, json }) => …)`; the module uses it to update its record **everywhere at once** (rows in other windows, the module's head and strip – folders: name, colour classes, symbol; a move reloads the folder windows; the controller answers the data, e.g. `folder: {id, name, rowClass, icon (svg), moved}`). **Without JavaScript** the form still posts: keep `<noscript><button type="submit">Speichern</button></noscript>`. Folder and Papierkorb properties are the reference (`folders/index.blade.php`, `folders/trash.blade.php`).
- **Eigenschaften-Karte (points 122.4, A252)** – the typed values of one document in its detail window (`documents/_properties.blade.php`): a **foldable card** (point 132: `<x-fold-card fold="detail.properties" class="doc-properties" :data-doc-properties="<GET url>" :data-document="<id>">`, the small quiet button "+ Eigenschaft" `data-mark-as="<id>"` in its `action` slot; the reload draws the whole card again with the remembered fold state; in the styleguide shown with the older `.doc-properties-head`) and `<ul class="prop-list">` of **property value rows** `<li class="prop-row">`: `.prop-name` (muted, fixed width) and `.prop-value` with a click-to-edit value (empty = removed). Only properties with a value show. A **suggested** value (`prop-row is-suggested`) is grey italic with `pill pill-new` "vorgeschlagen" and a ✓ (`control-button` in `form[data-prop-action]`) to confirm; the X to remove sits in `.row-actions`. A row with `data-page` + `data-box` has an orange name; a click emits `DocHamster.emit('document:highlight', { win, page, box })`. The card has **no ids** and reloads itself (JSON `{html}`) on `DocHamster.emit('properties:changed', { win, documentId })` in every window that shows the document.
- **Popup "Markieren als" (point 122.4)** – `DocHamster.markAs({ win, documentId, text, page, box, anchor })` (`modules/properties.js`): a framework dialog (`dialog mark-as`, built in JavaScript, with X) with the clicked text (`.mark-as-text`, orange bar), the active properties this document may carry as picked choice rows (`pick-list mark-as-list` of `label.pick-row` with a radio; second line type and current value), and a **Wert** field (`field-addon` with state symbol) that checks live on the server: `is-ok` + hint "Wird gespeichert als: …" or `is-error` + the reason; a choice shows its values as a `select`. Save stores a confirmed value (with page/box), toasts, emits `properties:changed` and resolves with the answer (null when closed). Any module may call it, e.g. from a clicked word.
- **Preview overlay (points 121.2, A240)** - `DocHamster.viewer` (`modules/document-viewer.js`) lets modules point at places on the document in the detail window: `frameIn(win)`, `page(frame)`, `goTo(frame, page)` (Promise, true when drawn), `layer(frame)` (the page element of `.doc-layer`, which zooms and pans with the picture or pdf canvas), `pointAt(frame, event)` (page-relative point), `reveal(frame, box)`, `source(frame)` (shown picture for crops). Boxes are page-relative `{x, y, w, h}` (0..1) like the OCR words. Marks: `<div class="doc-mark">` in percent of the page - semi-transparent orange with an orange frame (hover, selection), `doc-mark is-pulse` pulses briefly (`document:highlight`); `doc-mark is-faint` is lighter (a word read with low confidence, e.g. in the Live card of Texterkennung, point 124). Events: `viewer:page { frame, page }`, `viewer:box { frame, page, box, add(label, run) }` (a module adds an action to a marked area).
- **Reading view and word pill (points 121, A241-A243)** - `<div class="ocr-read" data-ocr-read="<words url>">` (`documents/_ocr_read.blade.php`, `modules/ocr-text.js`): the recognised words laid out like on the page (monospace `.ocr-line` rows, x gaps as spaces, `.ocr-page-break` between pages). Each word is a `.word-pill` (no layout shift): `is-hover` orange tint (with the preview mark; amounts and IBANs as one group), `is-selected` stronger tint with an orange underline (never filled orange), `is-unsure` dashed underline (confidence < 60), `is-learned` dotted underline (a correction learned from this sender is offered), `is-fixed` small orange dot (corrected). Point 134: the text is never edited as a block – words are corrected one by one in the word popup; without word positions the plain text shows read-only (`p.is-plain`). A280: dragging across the words makes a normal browser text selection (Ctrl+C copies it with line breaks: words of a line by one space, lines by a line break) and shows the Auswahl-Leiste with "Kopieren" and "Markieren als …" (union box of the selected words). A281: "Alles kopieren" (`icon-button ocr-copy` `data-ocr-copy`, symbol `copy`, tooltip) at the right end of the section head copies the whole text.
- **Word popup (points 122.3, 122.7)** - a framework dialog `dialog word-popup` (built in JavaScript, with X): an enlarged crop of the spot (`.word-crop-box > canvas.word-crop`, the word framed orange), the word in a `field-addon` with live type hint (IBAN mod-97 `is-ok` / `is-error`, amount, date), notes (`.word-popup-notes`: `pill pill-warning` "unsicher erkannt", "Original: …" with "Original anzeigen" = undo, a learned suggestion with "Vorschlag nehmen") and the actions "Übernehmen" (quiet, only when changed; stores the correction) and "Markieren als …" (stores a changed correction first, then `DocHamster.markAs`). Several words (shift-click, or "Text auswählen" on a marked area) give one value with the union box.
- **Auswahl-Leiste (point 134, A280)** - `DocHamster.selectionBar.show(rect, [{ label, icon, run }])` (`core/selection-bar.js`): a small floating toolbar `<div class="selection-bar" role="toolbar">` of quiet small buttons (`button-quiet button-small`, symbol + text) on the surface colour with a shadow, centred above a text selection (below it when there is no room). One for the whole page, in the top layer like the tooltip; it hides on `selectionBar.hide()`, Escape, scrolling, resizing and when the selection goes away, and its buttons never take the selection away. `DocHamster.copyText(text)` copies to the clipboard (Promise → false when refused). Used by the reading view ("Kopieren", "Markieren als …"); any module with selectable text may use it.
- **Vorschlags-Chip (point 120.4, A247)** – `<button type="button" class="suggest-chip">340,00 €</button>`, several in `<div class="suggest-chips" role="group" aria-label="…">` (optional first `<span class="suggest-chips-label">` on its own line): a value the app found that one click takes over (another amount on the document, a repaired IBAN). Dashed orange outline, never filled (it proposes; the main button decides), `aria-label`/tooltip say what the click does. A chip with `data-page` + `data-box` may show its place via `document:highlight`.
- **QR-Karte (point 120)** – `<figure class="qr-card"><img src="…svg" alt="…" width="240" height="240"><figcaption>Mit der Banking-App scannen</figcaption></figure>`: a QR code made on our server (never an external service, D-020), **always dark on white** – also in dark mode, scanners need the contrast. `qr-card is-missing` (a `div` with an icon and a `p`) stands in its place while the code can't be made and says what is missing; `is-stale` fades the code while it is redrawn.

## 4. Layout

- **The main menu has no sub-items** (PO, 2026-11-07). Every sub-area, entry and record opens on the right as a window.
- Left: the main menu. Its wall can be dragged: wide = open, narrow = icons only, too narrow = hidden (then a floating menu button). Phones: a drawer.
- The content starts below a gap as high as the dark bar, so the floating menu button never covers a title; scrolling takes everything to the very top.
- Width too small: the window row never scrolls sideways (point 64); windows shrink and become strips instead (§5).

## 5. Window system

- **Search in the toolbar** – `<x-window search="Placeholder">`: a small search field in the window toolbar with X (close) and magnifier (search) inside; Enter or the magnifier reloads the window body with `?q=…`, the module reads `q`. Optional search panel behind a chevron (slot `searchOptions`, prop `search-params`), see below.
- **Progress dialog** – a dialog without `data-dialog` (not closable) with a `<progress>` and a step line, for long server work (update install).

The general logic of the app (points 22, 24, 40, PO 2026-11-08): **every window is an area of its own** – it scrolls by itself and closes by itself, without touching the others.

**Principle (PO, 2026-11-11, must hold for every module):** every window in the row is **one instance of a module bound to one resource** (folder window = folder module for folder X, detail window = detail module for file Y), like Explorer windows: same code, look and functions per instance, each works on its own inside its column. Several windows of the same module side by side must work – **including the same folder or document twice**: a click always opens a **new** window to the right, never just focuses an existing one. The row is a path/history: a **main-menu choice drops the whole row**; opening something in window N closes everything right of N and opens the new window at N+1.

**Modules (PO, 2026-11-12, points 71, 73):** folder windows, document details, the settings levels and pages, and the **whole notes board** are modules. A module's inner parts (e.g. the notes columns) are plain content, never modules, and never fold. Every module window behaves like a Windows window: **minimise, maximise, close** – nothing else (point 74: no pin; maximise does its job). Windows stay in a row (no free desktop) and are loaded via fetch.

- A link with `data-window` in a window **closes every window right of that window** and opens the new window on the right – always a new instance, also when the same address is open already. Which windows become strips decides the width rules below.
- **Widths like Apple's split view (NSSplitView; points 54, 55, 64, A91–A94).** Every window declares **min, optimal, max** width and a **priority** (`<x-window>` props `min`, `optimal`, `max`, `priority`; defaults per `kind`: `folder` 20/26/34rem prio 1 · `trash`, `mail` 22/30/40rem prio 1 · `notes` 22/40/96rem prio 1 · `detail` 30/44/64rem prio 2 · `text` 32/48/72rem prio 2 · others 24/32/48rem prio 1). The row **never scrolls sideways**: the windows always share exactly the width there is. A window keeps its width from one layout to the next; only the difference is shared out (open, close, minimise, restore, browser/menu resize):
  - too little room → windows shrink towards their min, **lowest priority first, among equals from the left**; still too little → the lowest-priority window becomes a **strip** – never the newest or the one just opened/opened again (that one keeps its width, at most its preferred, while the others make room);
  - more room → a strip the layout made opens again as soon as the wide windows **at their min** leave room for its **min + 4rem** (A96: hysteresis, almost where it collapsed; a window that keeps its width or was sized by hand counts with that width, at most its preferred); then windows grow back to their preferred width, then to their max; the rest goes to the last wide window;
  - a click on a strip opens it again at its preferred width; the others make room by the same rules.
- **Dragging an edge (A91–A94):** computed from the state at drag start plus the whole distance, so the edge stays under the pointer; windows left of it never move. Wider: the windows right of it give way, lowest priority first (among equals from the left), each down to its min; then the edge stops, and **3rem** further the lowest-priority one snaps to a strip (never the newest). Dragging back until its min fits snaps it (and strips the layout made on the right) open again at its min – a 3rem band in between. Narrower: the right neighbour takes the room. During a drag nothing else lays out; on release the width is stored for **that window only**. The last window has no edge. Each window lies above the next one (descending `z-index`), so the edge's right half over the neighbour stays grabbable (A95).
- **Measuring jumps (point 63 / A90):** `?debug=layout` switches a measurement on for the tab (`?debug=off` ends it): user actions, window size changes and strips, layout shifts and elements gone and back within 300 ms; a small panel bottom right copies the log ("Messung kopieren") or empties it.
- **Strip:** the unfold arrow **›** (`chevron-right`) on top on the head line opens it again, then icon and title turned by 90°, the small X.
- **Head (like Windows, points 42, 70, 72, A116–A124):** icon, title (always visible, ellipsis), then on the right the three **window controls**, always in this order and look (frameless `control-button`s, 36 px): **minimise** ‹ (`chevron-left`, "Minimieren"), **maximise** (`window-maximise`: four small chevrons pointing out to the corners, "Maximieren"; while maximised `window-restore`: four chevrons pointing in, "Wiederherstellen", `aria-pressed="true"`; own SVGs in Tabler style with the stroke of ‹; on hover they pulse outward / inward, with "reduce motion" only the colour changes – points 87, A179, A180), **close** X (`x`, only with a `close` target). The line of the settings column heads.
  - Minimise makes the window a strip and it **stays** one until it is clicked.
  - Maximise: this module fills the row, **all others become strips** (`data-maxed` on the window, `is-maxed` on the row, no drag edges). A second click, or a **double-click on the title**, restores every window's strip state and width from before. Opening a window, clicking a strip, minimising or closing ends the maximised state; a reload keeps it.
  - **Phones (< 64rem):** only the back arrow (left) and X; no minimise, no maximise.
- **Toolbar (point 41):** the search field, the module's buttons (`actions`, small 36 px icon buttons) and, at the right end, the module's ⋯ menu stand in a row below the head. It follows **the window's own width** (container queries on `.win-frame`, container `win`), not the screen: wide = one row (search left, buttons right); below 44rem the search takes its own row; below 28rem the window is **narrow**: elements with `win-wide-only` hide, elements with `win-narrow-only` show. Use that to turn a button group into one dropdown button and extra buttons into entries of the module's ⋯ menu (slot `menu`) (reference: the view switcher and "Neues Dokument"/"Neuer Ordner" in `documents/index.blade.php`). The toolbar wraps before anything is cut at the window edge.
- The window just opened or opened again scrolls into view.
- **Width by hand (points 44, 54.5):** every wide window has a drag edge on its right (`.win-edge`, same look as the wall right of the menu): drag or arrow keys (Shift = bigger steps) set its width by the drag rules above – also below its min (at least 12rem); double-click goes back to the module's optimal. The width belongs to **that one window** (A97: `data-window-hand`, kept in the tab's window history in `sessionStorage`, so it survives a reload); for the layout it **is** that window's preferred width. New windows always start at their kind's optimal width. Not on phones.
- **Window state lives in its address (point 52):** a module setting that belongs to one window (e.g. the list view `?view=timeline`) is a query field of the window URL, so each instance keeps its own and reload keeps it; changing it reloads only that window (`DocHamster.reloadWindow(win, url, '.win-frame')`). A window without it starts with the person's last choice.
- The **X** in a window's head closes just that window; the small X on a strip removes it from the history. If no wide window is left, the nearest strip opens. **Every module has an X** (point 112), the first window too; closing the last one leaves the area empty, without a hint (A219) – the main menu opens the next.
- **Opener row (Öffner-Zeile, point 141, A306, A307):** the row, tile or link in window N whose click opened window N+1 stays marked while N+1 is open – the marked-row look (point 155: white surface, shadow, orange symbol; a `tr` gets the white surface on its cells). The window system does it for every module: the row is the link's closest `[data-window-row]`, `li` or `tr`, else the link itself (`a[data-window]` in the head, toolbar, search panel or a menu marks nothing); give a module's row element `data-window-row` when it is no `li`/`tr`. Each window remembers its opener (`data-window-from` = window id, `data-window-opener` = link address, kept in the tab's history), so the mark moves with the next click, goes with the child, and comes back after a body reload (search, view switch, `DocHamster.reloadWindow`) or a page load – found again by the link address (exact, else same path with the most equal query fields). The mark stays for good (point 162): the hover does not change it and it wins over a coloured row and the open-document tint. When both windows stand next to each other on a wide screen, the opener window shows a short orange line on its right edge at the row's height (`has-opener-line`, `--opener-y`), like the Finder's column view – the row itself has no notch any more (point 162; windows.js still sets `is-linked`, no CSS uses it); the line hides when the row is scrolled out of view, a window is a strip, or the windows are not adjacent. Modules do nothing.
- The **active** window is the one opened last or clicked into; the browser address and the title follow it. Browser back opens the window of the entry before (the entry names the window, so two windows with one address work). A reload keeps the history of this tab with which windows were minimised or maximised (`sessionStorage`); windows not loaded yet load when they are shown. A link in the main menu drops that history.
- Changes glide (view transitions where the browser has them; none with "reduce motion").
- **Vorladen and the window cache (point 164.8, A342; `core/window-cache.js`):** windows.js loads every window through `DocHamster.windowCache.take(url)`. A window kept in memory opens at once and refreshes quietly afterwards (the server answers 304 while unchanged; new content replaces `.win-frame`/`.win-body` only while the person hasn't touched the window). Filled by hover intent (80 ms) or touch on `a[data-window]`, the small windows (menu windows, Dokumente, Bank) once per tab session, the window this person usually opens next (learned per user), and with "Stark" the window links of the active window while idle. Any non-GET fetch or posted form drops the cache – a module needs to do nothing. Prefetch requests carry `X-DocHamster-Prefetch: 1`: **a GET with a side effect (mark as seen, opened) must skip it when `App\Http\Speed\Prefetch::is()`**. Option: Einstellungen → Geschwindigkeit → Vorladen (`<body data-prefetch>`); data saver, 2g or a slow server → hover intent only. Main-menu links: browser prefetch on hover (speculation rules); a link that must not be prefetched gets `data-no-prefetch`.
- **On its way (point 164.8d):** the clicked row gets `is-pressed` at once; after 150 ms a thin orange bar runs along the top of the row of windows (`.windows.is-loading`).
- Phones: one window at a time, with a back arrow in its head (opens the window left of it).
- Without JavaScript every link is a normal page; the page shows its windows side by side.

### How a module uses it

**Page:** wrap the windows of a page in `<div class="windows" data-windows>` and set `@section('main_class', 'page-windows')`. The page's **last** window is the page itself.

```blade
@section('main_class', 'page-windows')
@section('content')
    <div class="windows" data-windows>
        <x-window :title="__('documents.title')" icon="receipt" :url="route('documents.index')">
            <x-slot:actions>…filter, view…</x-slot:actions>
            …the list…
        </x-window>
        @if ($open)
            <x-window :title="$open->title" icon="file-text" :url="route('documents.show', $open->id)" :close="route('documents.index')">
                …the receipt…
            </x-window>
        @endif
    </div>
@endsection
```

**Links that open a window:** `<a href="…" data-window>`. The framework loads the target in the background with the header `X-DocHamster-Window: 1`; the layout then returns only the content (no menu, no frame), and the framework takes the page's last `section[data-window]`. Every click loads a new instance, even for an address that is open already. Modules need no extra route or controller code.

**`<x-window>` props:** `title`, `icon` (Tabler name), `url` (this window's address; default the current one), `close` (where the X leads without JavaScript; always set, point 112), `upload` (where an upload belongs while this window is active, as form fields, e.g. `upload="folder=01H…"`), `min`, `optimal`, `max` (widths for the automatic layout, e.g. `min="36rem"`) and `priority` (higher = becomes a strip later), defaults per `kind` (see the width rules above), `kind` (module type, e.g. `folder`, `detail`; default the route name), `search` (placeholder of a search field in the toolbar, see below), `search-live`, `search-params` and slot `searchOptions` (search panel, see below), slot `actions` (buttons in the toolbar), slot `menu` (the module's entries of its ⋯ menu, below the framework's "Notizen daneben öffnen"), extra classes via `class="…"`. Every window has the toolbar row (at least the ⋯ menu).

**Notes module (points 71, 73, A121, A122, A200):** it can be open several times; the main menu "Home" opens it as the first module. The ⋯ menus no longer carry a "Notizen daneben öffnen" entry.

**Search field (A104, points 102–106):** `<x-window search="Ordner und Belege suchen">` puts a small search field (`input-small`) in the toolbar, a Field with symbol: **X** (`data-window-search-clear`, shown while a search is set) and a **magnifier** submit button inside; in a window below 44rem it gets its own row. **Enter or the magnifier** searches: the framework loads the window's address with `?q=…` (same `X-DocHamster-Window: 1` fetch as window links) and swaps **only the body** (`.win-body`), so the field keeps focus and caret; the address follows with `replaceState`, reload and the stored history keep `q`. A new search drops `page`. `search-live` (prop `searchLive`) makes typing search too (300 ms pause); default off (A203). The X or Escape in the field **closes the search**: it empties the field and the panel and loads without `q` and the panel's parameters, so the window's own view (e.g. `?view=…`) comes back. Any other element with `data-window-search-clear` inside the window does the same (e.g. an X link in the head of a result list; give it the address without the search as `href` for no-JS). Every window has its own search; the new body gets `window:open`.
**Search panel (points 102, 135, A282-A285):** slot `searchOptions` adds a chevron button beside the field that opens a panel **inside the same form** with the module's fields. Its layout: on top a row that is **always visible** (`.search-top`, e.g. the ticks "Auch im erkannten Text" and "In allen Ordnern"); below it the module's sections as **compact foldable cards** (`.search-sections`, `<x-fold-card compact :remember="false">`), **folded at first, open by themselves when a filter in them is set**, each head with a summary of what is set (e.g. "Zeitraum: Dieser Monat · Belegdatum", "Tags: 2 gewählt"); stacked in a narrow window, two columns from 44rem (A285). Inside a section the lines are `.search-line` (label column + control, small fields, A284) and choices are **button groups as a choice** ("Alle | Ja | Nein", "Alle | PDF | Bild" – never "egal" selects or radios). At the bottom, **fixed** while the panel scrolls (`.win-search-actions`, from `<x-window>`): "Zurücksetzen" and the **magnifier** search button. Name the fields in `search-params="ocr all"`: they are sent with `q` (empty ones are dropped from the address), kept out of the form's hidden fields, dropped when the search is closed, and the chevron is marked (`is-active`) while one is set. After a reset or a removed chip the framework calls `DocHamster.syncChoices(area)` and emits `search:reset` (area) so the module can update its summaries. Reference: `documents/index.blade.php` + `modules/documents-search.js` (period buttons Dieser Monat | Letzter Monat | Dieses Jahr | Letztes Jahr | Eigener – date fields only for "Eigener"; property filters: "+ Filter hinzufügen" picks a property and shows one `.search-prop` row with the input of its type, "Alle | hat Wert | fehlt" and an X). **What is found is the module's job:** its controller reads `q` and its own parameters (and must render the search field's window again with the filtered body). Without JavaScript the field is a normal GET form (the panel needs JavaScript to open).
- **Search button rule (A305):** a button that runs a search is **always the magnifier icon** (`search`) with the tooltip and label "Suchen" – never the word "Suchen" or "Filtern" as text. This holds for the window search field, the search panel and filter forms on pages (e.g. Einstellungen → Log).

**Uploads:** "Beleg hochladen" in the menu takes the `upload` fields of the **active** window and sends them along; files dropped go where they are dropped (see "Upload by drop"). Which fields a window sets and what the server does with them is up to the module.

**JavaScript of a module:** windows arrive after the page has loaded, so "run on DOMContentLoaded" is not enough. Register instead:

```js
DocHamster.on('window:open', root => {
    root.querySelectorAll('[data-my-thing]').forEach(setUp);
});
DocHamster.on('window:close', root => { /* clean up timers etc. */ });
```

`window:open` runs for every window of the first page and for each window loaded later (`root` is that window; on pages without windows it is `document`). Prefer delegated listeners on `document` where you can.

**IDs (multi-instance):** a window can be open twice – also with the **same** record. Write ids, `for`, `form`, `aria-*` references and dialog names as usual (with the record's id where it helps reading); the framework gives every id in a window a per-window suffix and rewrites the references in that window (`for`, `form`, `list`, `aria-labelledby/-describedby/-controls/…`, `href="#…"`, `data-copy`, `data-focus`, `data-dialog`/`data-dialog-open`). A dialog opener finds its dialog in its own window first. In module JavaScript never look up window content with `document.getElementById` or `document.querySelector` – start from the window (`root` of `window:open`, or `el.closest('section[data-window]')`) and keep state per element (`WeakMap`), not per page.

### Reference module

Belege (`resources/views/documents/index.blade.php`, `_detail.blade.php`): the list is the root window, a receipt opens as a window to its right. Notizen (`resources/views/home/index.blade.php`, `kind="notes"`): one window for the whole board; its JavaScript (`setupBoard` in app.js) runs per board on `window:open` and only looks inside its own window, so several boards side by side work (drag & drop, dialogs, column titles, tag filter reloading only its own window).

Bank (`resources/views/bank/index.blade.php`, points 129, A267–A274): the Bank window lists the accounts (row with `badge badge-alert` = open bookings, A274), an account opens as a window (`kind="bank-account"`, search + status filter in the search panel), a booking as a window (`kind="bank-transaction"`) with Eigenschaften rows, linked documents (suggested: `pill pill-new` + "Bestätigen" + X), the sums of an n:m link (difference as `pill pill-warning`, balanced `pill pill-ok`) and "Dokument zuordnen". Its forms carry `data-bank-action` (sent in the background by `modules/bank.js`, toast, Bank windows reload; without JavaScript they post and redirect).

Posteingang (`resources/views/inbox/index.blade.php`, `kind="inbox"`, `modules/inbox.js`, point 153): one window with everything that came in, newest first. A tab bar per source (Alle · Upload · Drucker · E-Mail · Handy) whose tabs carry the red `badge badge-alert` of that source (`data-badge="inbox-<source>"`, main menu `inbox` = the sum; viewing a tab marks it seen); tabs, ✓ "Erledigt" (row action via `documents/_row-actions` with `inboxDone`), "Alle erledigt" and the head's upload reload only this window (`.win-frame`). Rows are the ordinary document rows (`data-doc`: drag onto folders, rename, details) plus the source icon (`type-icon` with tooltip). Sources are set up under Einstellungen → Eingang.

Einstellungen (`resources/views/layouts/settings.blade.php`, point 156): a row of windows built from the building block **Menü-Fenster** – the groups (menu window, tiles), the entries of a group (menu window, list; skipped for a leaf group or a group with one entry), then the page (`class="win-page"`, title and icon from the menu entry). A page with a list of its own (Tags) puts it into `@section('pane')` (own window before the page, toolbar from `@section('pane_actions')`); `@section('page_title')` names the page window. The red counts lead down: group tile → entry row (`Badges::SETTINGS`). Old settings addresses keep working: each renders its whole row, a window link takes the last window.
