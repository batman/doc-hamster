### D-003 · Database default — Owner: Lead
- **Status:** decided (Lead, 2026-10-29)
- **Input:** SQLite default (FTS5), MariaDB/MySQL supported; no DB-specific SQL outside the search adapter.
- **PO input (2026-10-29, Q-8):** stick to common standards; MariaDB is expected as the prerequisite; support several databases if the effort is small.
- **Decision:** **MariaDB and MySQL**, both supported from v1, via Laravel's `mariadb` and `mysql` drivers.
  - **Minimum versions:** MariaDB **10.11** LTS (community support until 2028-02; default in Ubuntu 24.04 LTS and Debian 12; Debian 13 ships 11.8) · MySQL **8.4** LTS (8.0 reached end of life in 2026-04). Recommended: the newest LTS the server offers. Laravel itself accepts older versions (MariaDB 10.3+, MySQL 5.7+), but those no longer get security fixes.
  - **Compatibility:** MariaDB started as a fork of MySQL; for ordinary applications both are interchangeable, but they have drifted apart since MySQL 8 (JSON functions, some SQL functions, default auth plugins). We stay in the **common subset**: InnoDB, `utf8mb4`, standard SQL via the query builder, `FULLTEXT` indexes with `MATCH … AGAINST` for search (works on both), JSON columns only stored/read whole – no DB-specific JSON functions in queries. CI runs the test suite on **both** (MariaDB 10.11 + MySQL 8.4) – that is the "small effort" for the second database.
  - **Search quality:** MariaDB/MySQL `FULLTEXT` has no German stemming. AK-4.3.1 says "wenn möglich" – we normalise words in PHP before indexing (lower case, umlauts, simple suffix rules) if tests show it is needed.
  - **Not supported in v1:** SQLite (different full-text engine, would need a second search adapter) and PostgreSQL. Code stays DB-neutral (search behind a `SearchIndex` interface), so PostgreSQL could follow later if wanted.
  - Supersedes the earlier SQLite proposal. PLAN.md §3 principle 7 ("SQLite-Standard"), §5.1, §5.2, §6.2 `documents_fts`, §12 and §13 (CI "SQLite + MariaDB-Matrix") need updating in P0-1c, see PLAN-REVIEW B11.

### D-010 · Target hosting & network — Owner: Lead
- **Status:** decided (Lead with PO, 2026-10-29)
- **Question:** Home server/NAS on the LAN, VPS, or shared hosting? Decides whether OCR tools can run on the server **and how the phone web app reaches it** (see D-017).
- **Options:** A) VPS/home server with Docker · B) VPS without Docker · C) shared hosting (OCR likely impossible) · D) NAS.
- **Note:** The concrete server (provider, domain, IP) is **not** recorded here – only the chosen variant.
- **PO input (Q-8, 2026-10-29):** follow common standards, as compatible as reasonable; publish one minimum requirement; the phone must reach the server from anywhere; **no Docker needed**; the app detects its environment itself and offers only add-ons that work there.
- **Decision:**
  - **One app, one minimum requirement, no hosting types.** DocHamster runs anywhere the minimum below is met: own server (VPS, home server, NAS) or web hosting. There is no "server edition" vs "hosting edition".
  - **No Docker in v1.** Standard install = upload/clone the code, `composer install`, `.env`, `php artisan dochamster:setup`, cron entry. Install docs for a plain Linux server (Debian/Ubuntu) and for typical web hosting. A Docker setup may come later as a convenience, not as a requirement.
  - **Environment detection:** `dochamster:doctor` (at setup, after updates, and on the admin page) checks PHP version and extensions, DB version, cron heartbeat, HTTPS, upload limits, `proc_open` and the external tools. Add-ons whose requirements are missing are **not offered or shown greyed out** with the reason ("Texterkennung braucht Tesseract – auf diesem Server nicht vorhanden"). The core flow never depends on an add-on.
  - **Core (always available):** capture + offline queue, time/location, Revolut sync and matching, receipt pack PDF (pure PHP), search, tax advisor access, mail.
  - **Add-ons (only if the environment has them):** OCR (Tesseract 5 + ocrmypdf), local speech-to-text (whisper.cpp + ffmpeg, D-019), HEIC conversion of file uploads (libheif/vips), faster image processing (vips instead of GD).
  - **Background work runs via cron:** `schedule:run` every minute starts short queue runs (`queue:work --stop-when-empty --max-time=50`). A permanent worker process (systemd/supervisor) is optional for own servers. Long jobs (OCR, STT) are split per page/file so they fit hosting time limits.
  - **Hard requirement:** a fixed domain name with a publicly trusted TLS certificate, reachable from the internet via HTTPS. Reason: passkeys are bound to the domain (changing it later breaks all passkeys), the PWA/service worker needs a secure context, and the phone sends documents from anywhere.
  - **Minimum requirements** – published in the README, checked by `dochamster:doctor`:

    | Area | Minimum | For add-ons / recommended |
    |------|---------|---------------------------|
    | Server | Linux server or web hosting with SSH and cron (every minute) | own server for OCR/STT add-ons |
    | CPU / RAM | 2 cores, 2 GB RAM (excl. DB) | 4 cores, 6 GB for local STT |
    | Disk | 10 GB + receipts (≈ 2 MB per receipt) | SSD |
    | PHP | 8.4 with `pdo_mysql`, `mbstring`, `intl`, `sodium`, `fileinfo`, `exif`, `zip`, `gd`; `memory_limit` ≥ 256 MB; `upload_max_filesize`/`post_max_size` ≥ 26 MB | `vips` extension; `proc_open` allowed (needed by all add-ons) |
    | Database | MariaDB 10.11 or MySQL 8.4 (D-003) | newest LTS |
    | Network | own domain, publicly trusted TLS, inbound HTTPS; outbound HTTPS to the Revolut API, SMTP | – |
    | Add-on tools | – | Tesseract 5, ocrmypdf, ffmpeg, whisper.cpp, libheif |
    | Phone | current iOS Safari / Android Chrome (last 2 major versions) | installed as home-screen app |

    Estimates to verify in P1 on the PO's test server (its details stay out of the repo).
  - **Data files:** GeoNames place names (D-017) are loaded by the setup/update command (pinned version + checksum), Tesseract language data and the Whisper model by the add-on's install step. Nothing is downloaded while processing documents.

### D-016 · Revolut connection — Owner: Lead (technical), PO (account type)
- **Status:** decided (Lead, 2026-10-29)
- **Goal (PO):** For every Revolut payment, get the full transaction details (merchant, amount, currency, original amount + FX rate, fee, exact time, Revolut category, status, merchant location if available) and match them with the receipt photo.
- **Ways to evaluate (Lead decides):** Revolut Business API (business accounts only) · Revolut statement export (CSV/Excel, works for personal and business, manual upload) · open-banking (PSD2 account information) provider for personal accounts.
- **Constraints:** read-only access; credentials encrypted on the server, never in the repo; file import always available as fallback.
- **Target account type (PO, 2026-10-29):** Revolut **Business** → the official Revolut Business API is available and is the expected primary way; file import stays as fallback. Open banking for personal accounts is out of scope for v1.
- **Still for the Lead:** API access setup (certificates/tokens, refresh), sync interval, which fields the API really delivers (merchant location?), sandbox for tests.
- **Decision (Lead, checked against the official Business API docs on 2026-10-29):**
  - **Where it lives (D-021):** everything below describes the **Revolut module** (own repo, installed on demand). The core knows no Revolut: it only offers the `BankConnector` interface, a generic "Bankverbindung" settings page the module fills, and the `net` queue the module's jobs run on (D-020). The module registers its own callback route and settings. Interface details: Q-11.
  - **Primary: Revolut Business API, read-only, polling.** File import (CSV/Excel statement) stays as fallback and for history.
  - **Access setup (one-time, by the owner in Settings):** the app generates an RSA key pair and shows the public certificate; the owner adds it in the Revolut Business web app (Business API settings) with the redirect URI the module registers (e.g. `https://<our domain>/settings/bank/connectors/revolut/callback`), then pastes the Client ID; the app opens the consent page with **`scope=READ`** (no WRITE/PAY – a leaked token can't move money). The callback stores the authorisation code (valid 2 min) and dispatches a high-priority `net` job that exchanges it – `app` itself never calls Revolut (D-020). The consent URL carries a random `state` kept in the owner's session; the callback requires a logged-in owner of that org, compares `state` in constant time and accepts it once. The code is kept only encrypted (job payload encrypted, `ShouldBeEncrypted`), never logged, and the callback redirects at once so the `?code=` URL doesn't stay in the browser.
  - **Tokens:** access token lives 40 min; refresh token does not expire. Store refresh token and private key encrypted (D-007); sign a fresh client-assertion JWT with a short `exp` (5 min) for every refresh. Refresh invalidates the previous access token → only one process refreshes (lock). If refresh fails (consent revoked), the connection goes to `status = error` and the owner is notified. Optional IP allowlist: owner's choice, only with a static public IP.
  - **Sync:** A `net` job polls `GET /transactions` (via cron, D-010) every 15 min, plus right after each photo upload (debounced 1 min), window = last sync − 3 days overlap; pages with `to = created_at` of the last item, `count = 1000`, and the next page overlaps by the last item's timestamp (upsert removes the duplicates, so no row with an equal timestamp is skipped). The time filter works on `created_at`, so long-running card holds (hotel, fuel, car hire) can drop out of the window: every transaction still `pending` is re-fetched one by one (`GET /transaction/{id}`) until final (`completed`/`declined`/`failed`/`reverted`). Upsert by Revolut `id` (`external_id`). No webhooks in v1: polling is simpler, needs no signature handling and works in every supported environment (D-010).
  - **Fields we get** (`card_payment` example): `created_at` (authorisation time → used for matching), `completed_at`, `state`, `merchant.name/city/country/category_code` (MCC), per leg `amount` + `currency` (account side), `bill_amount` + `bill_currency` (original currency), `fee`, `description`. The transaction object has **no Revolut spending category**; we store the MCC as `provider_category` and show it as readable text via an MCC → German label table (PLAN-REVIEW B19, PO agreed in Q-10). Cardholder name/phone are **dropped** before storing `raw_json` (PLAN-REVIEW B8).
  - **Tests:** unit/feature tests use recorded, synthetic API responses (no network in CI). Manual end-to-end check against the Revolut **Sandbox** (needs a free sandbox account, owner/PO creates it; credentials never in the repo).
  - **Watch out:** on the Freelancer plan, history older than 90 days is only readable within 5 min of the first authorisation (PSD2) → the app runs a full history import right after consent. The Expenses API (receipts inside Revolut) is not used: photos stay on our server (D-019).
  - **Sources (official docs, read 2026-10-29):** setup, token lifetimes, "refresh token does not expire", "refreshing invalidates the previous token": <https://developer.revolut.com/docs/guides/manage-accounts/get-started/make-your-first-api-request> · scopes READ/WRITE/PAY, transaction fields, paging, max 1,000 per request: <https://developer.revolut.com/docs/business/get-transactions> · Freelancer 90-day rule: <https://developer.revolut.com/docs/guides/manage-accounts/accounts-and-transactions/retrieve-transactions> (seen in search results, re-check when implementing P3-3).
- **Changed 2026-10-29 (P0-15):** reworded as the Revolut **module** behind `BankConnector` (D-021); LAN/VPN remark removed (D-010 requires public HTTPS); OAuth `state` check and encrypted code added (security detail from the Lead's re-check). Content of the Revolut decision unchanged.

### D-017 · Capture time & location; phone → server delivery — Owner: Lead
- **Status:** decided (Lead, 2026-10-29); camera method decided in P2-2 after a device test (PLAN-REVIEW B5)
- **Requirement (PO):** The web app records **when** the photo was taken and **where** (PLAN.md §4.1 "Aufnahme-Metadaten").
- **For the Lead:** Geolocation API vs EXIF (EXIF GPS is often stripped by browsers/iOS); clock-skew handling; how coordinates are stored (encrypted? rounded?); how the place name (city) is resolved without sending locations to third parties (offline data vs. self-hosted vs. external service); upload protocol and offline queue between phone and server.
- **Fixed by the PO:** location is opt-in, removable per receipt, and appears in the receipt pack only as a city name and only if switched on.
- **Decision (Lead):**
  - **Time:** at the shutter the PWA stores `captured_at` (device clock, ms) + IANA time zone (`Intl`) + UTC offset. EXIF `DateTimeOriginal` is read **in the browser before resizing** (canvas drops EXIF, B4) and sent as a cross-check. This only exists on the `<input capture>`/file path; the in-page camera (`getUserMedia`) has no EXIF at all, and iOS usually strips GPS from picked/captured photos – so EXIF is a time cross-check, rarely a location source. Part of the P2-2 prototype criteria. Every upload also sends `client_sent_at`; the server stores `skew = received_at − client_sent_at`, keeps the raw value and a corrected `captured_at`, and flags |skew| > 2 min. Source stays `device`/`exif`/`server` as in PLAN.
  - **Location:** `watchPosition` starts when the capture screen opens (only with opt-in), so a fix is usually ready at the shutter; at most 3 s wait, else saved without location and a late fix is attached if it arrives within 60 s. Stored: lat/lon/accuracy **encrypted** (app key, D-007), full precision; never logged.
  - **Place name without third parties:** offline reverse geocoding from the GeoNames `cities1000` dataset (CC BY 4.0, attribution in the app's About page and docs), loaded into a database table at install/update; nearest city by bounding box + haversine, in the `local` worker. No external geocoding service.
  - **Phone → server (answers Q-6):** HTTPS only, same origin as the PWA. **One request per file**, so a document with 20 pages or a 25 MB PDF never has to go up in one piece and an interrupted upload resumes at the next missing page (AK-4.1.4):
    1. `PUT /api/uploads/{client_upload_id}/files/{n}` – one page/file (raw body + content type); idempotent per (`org_id`, `client_upload_id`, `n`), a repeat with the same SHA-256 returns 200.
    2. `POST /api/uploads/{client_upload_id}/complete` – JSON with page count, capture metadata and `client_sent_at`; creates the document. A repeat returns the existing document (200) instead of a new one (201).
    `client_upload_id` is a ULID made on the phone. Limits written down in config and install docs: 25 MB per file (AK-4.1.6) → PHP `upload_max_filesize`/`post_max_size` and the web server's request body limit set to ≥ 26 MB (checked by `dochamster:doctor`); unfinished uploads are deleted after 7 days.
  - **Auth and CSRF for the API:** device cookie (D-009) + session. Queued uploads may be sent a day later, when the session's CSRF token is long gone (HTTP 419). Therefore `/api/*` does **not** use the session CSRF token; instead it requires same-origin (`Origin` header = our origin, `Sec-Fetch-Site: same-origin` where sent) plus a custom request header (`X-DocHamster-Client: 1`, which a cross-site form can't set). HTML forms keep Laravel's normal CSRF token. E2E test: queue offline, expire the session, go online → upload succeeds.
  - **Offline queue:** IndexedDB holds blobs + metadata until the server confirms. Sent on app open, on `online`, on `visibilitychange`, and via Background Sync where available (not on iOS). `navigator.storage.persist()` requested; the app recommends installing to the home screen (iOS evicts storage of non-installed sites). Badge shows queue length.

### D-020 · Egress control without containers — Owner: Lead
- **Status:** decided (Lead, 2026-10-29) – implements the "outbound only Revolut + SMTP" rule of D-019; no Docker (D-010)
- **Decision:**
  - Jobs are split into two queues: `local` (normalize, OCR, STT, geocoding, matching, receipt pack PDF) and `net` (Revolut token exchange and sync, all mail incl. invitations and export links). **Only `net` jobs may talk to the outside**; the Revolut API client and the mailer are only reachable from `net` jobs. Web requests (`app/Http`) never make outbound calls themselves – e.g. the Revolut callback dispatches a `net` job, mail is always queued, never sent synchronously.
  - **Enforcement in code:** an architecture test (Pest arch tests) fails if anything outside the `net` job classes uses the HTTP client, mailer or sockets. The external add-on tools (Tesseract, whisper.cpp, ffmpeg) are called with argument arrays and have no network features we use.
  - **Proof for AK-4.7.2:** CI runs the `local` job suite (OCR, STT, geocoding, PDF) inside a runner step with networking disabled; any outbound attempt fails the build. This is CI tooling only, not something users install.
  - **On own servers (optional, documented):** run the `local` worker as its own system user and block its outbound traffic with a firewall rule (e.g. nftables/iptables owner match), allow only Revolut API + SMTP for the `net` worker. On web hosting this isn't possible; there the code rules above are the protection – the doctor page says so.

  - **Where:** Settings → Organisation → "Backup herunterladen". Only for members with the role `owner` **of that organisation** – the instance admin gets no cross-org export (for whole-server disaster recovery they use `dochamster:backup`, below); requires a fresh passkey confirmation (step-up, PLAN §11.1) and is written to the audit log. Tax advisors and members never see it.
  - **Choice:** "Alles" (default) or period von/bis, plus a switch "Originale + abgeleitete Dateien" (default: originals only – thumbnails, searchable PDFs etc. can be regenerated).
  - **What goes in – the owner decides (operator answer, 2026-10-29):** checkboxes, **all ticked by default**, for both "Alles" and period backups:
    - "Genaue Aufnahmeorte (GPS-Koordinaten)" – unticked: only the place name is exported, **and** GPS/location tags (EXIF, XMP) are removed from the exported copies of the files (the stored originals stay untouched, PLAN §3); `document.json` gets `location_stripped: true`. CI test: a synthetic JPEG with GPS EXIF must not carry it in an unticked export.
    - "Papierkorb" – documents in the trash, marked as deleted in `document.json`.
    - "Protokoll (Audit-Log)" – the audit log entries for the period.
    The dialog explains next to each box what is missing after a restore if it is unticked; `manifest.json` records the choices, and `dochamster:restore` prints which parts were left out.
  - **Period rule:** a document belongs to the period by its capture date (fallback: document date, then upload date); a transaction by its booking date; receipt packs by the period they cover. Matches are included when both sides are in the ZIP.
  - **Contents of the ZIP:**
    - `documents/JJJJ-MM/<Belegnummer>_<Händler>_<Betrag>/` – original files, audio notes, `document.json` (metadata, fields, tags, capture data incl. place name, coordinates if ticked). Folder names are sanitised: merchant reduced to letters, digits, `-` and `_` (umlauts transliterated, everything else → `_`), cut to 40 characters; amount as `12,34EUR`. Documents without a Belegnummer yet (not `processed`, failed uploads) use `ohne-nummer_<ULID>` instead. Name collisions get a `_2`, `_3` suffix.
    - `bank/` – accounts (IBAN masked), transactions, matches as JSON **and** CSV (`;`, UTF-8 with BOM, opens in Excel).
    - `receipt-packs/` – the receipt pack PDFs created for the period.
    - `organisation.json` – categories, payment methods, rules, members (names/roles only), shares.
    - `manifest.json` – app + schema version, period, created at/by, file list with SHA-256; `LIESMICH.txt` explaining the structure.
    - **Never inside:** passwords/hashes, passkey keys, device tokens, bank connector tokens and keys, the app key. After a restore, devices are paired again, bank connections reconnected and **tax advisor passwords reset** by the owner (D-012) – the restore command and `LIESMICH.txt` say so.
  - **Size estimate:** shown live before starting and updated when the period changes: sum of the selected files' stored sizes (known from `document_files.size`) + estimated JSON/CSV size (row counts × average row size). Photos and PDFs are already compressed, so files go into the ZIP **without** recompression – the estimate is within a few percent; the real size is shown in the download dialog.
  - **Download now or later:**
    - Up to a limit (default **500 MB**, configurable, lowered automatically when `dochamster:doctor` sees a short PHP time limit): the ZIP is **streamed directly** – the download starts immediately and nothing is written to the server's disk (library `maennchen/zipstream-php`, MIT).
    - Above the limit: a `local` job builds the ZIP in steps (fits web-hosting time limits) and shows progress, then the owner is notified; the download is available for 24 h and the file is deleted afterwards.
    - **The download is not a bearer link.** It is a normal app route that works only for the **logged-in owner who started the backup** (session + policy check on `org_id`, `created_by` and that the user is still `owner` of that org at download time, fresh step-up; expiry checked against `created_at`, not just whether the file still exists), served with `Cache-Control: no-store`. No token in the URL, unlike the tax advisor export links (`/d/{token}`, §10.2) – a forwarded or logged URL is useless. The notification only says "Backup fertig" and links to the settings page.
    - **Guards before building:** only **one running backup per org** (a second request shows the running one); free disk space is checked against the size estimate **+ 20 %** before the job starts, otherwise the owner sees "Nicht genug Speicherplatz auf dem Server (benötigt ≈ X, frei Y)". Temporary files live in a private storage folder, never under `public/`.
    - **Cleanup does not rely on cron alone:** expired backup files are also deleted whenever a backup is started or the backup settings page is opened, and `dochamster:doctor` warns about any backup file older than 24 h.
  - **Encryption (option, recommended):** "ZIP mit Passwort schützen" → AES-256 ZIP encryption (PHP `ZipArchive`/libzip) with a password the owner types in twice (at least 12 characters; the dialog offers a generated passphrase to copy and says it can't be recovered). **Never stored, also not in the queue:** the build job's payload is encrypted with the app key (`ShouldBeEncrypted`), the password is a `#[\SensitiveParameter]`, the job has `tries = 1` and no `failed_jobs` row keeps the payload; a test searches `jobs`, `failed_jobs` and the logs for a known test password. **File names:** AES ZIP encryption hides only file contents, not names (month, merchant, amount would be readable) – so a protected backup is an outer ZIP with a short neutral `LIESMICH.txt` and one encrypted entry `backup.zip` that holds the readable structure. The streaming library can't encrypt, so a protected ZIP is always built by the background job (temporary file, deleted after download or 24 h), even below the size limit. Without a password, the dialog warns that the file contains all receipts and bank data unencrypted. **Opening it:** the Windows Explorer ZIP support has historically handled only the old ZipCrypto, not AES – we assume it can't open the file until a test in P4 shows otherwise; the dialog and `LIESMICH.txt` therefore name a free tool that can (7-Zip on Windows; macOS/Linux: Keka, `7z`). The password dialog says the tax advisor needs the same tool.
  - **Restore:** a full ("Alles") backup can be imported into an **empty** instance with `php artisan dochamster:restore <zip>`; period backups are archives (readable without DocHamster), not meant for restore. CI tests export → restore with generated data. The ZIP is treated as **untrusted input** (it may have been edited or come from elsewhere):
    - **Empty instance enforced:** the command refuses if any organisation, user or document exists (checked inside the restore transaction); it only inserts, never upserts, and fails on any ID collision.
    - **Paths:** every entry name is checked before anything is written – no absolute paths, no `..` segments, no drive letters or backslashes, no control characters, no symlinks or other special entries, no duplicate names, no names that collide after case-folding + Unicode NFC, and local header name = central directory name. Files go to a staging folder in private storage under **generated names** (mapped via the manifest), never under the ZIP's names; staging is deleted on success and on abort. Anything unexpected aborts the restore.
    - **Integrity:** `manifest.json` is read first; every file's SHA-256 and size are checked against it, and files not listed in the manifest are rejected. Nothing is written to the database until all checks passed (restore into the staging folder, then one DB transaction). The manifest proves **integrity, not authenticity** – whoever edits a file can edit the manifest too – so the content is checked as well:
    - **Content:** every file passes the same type allowlist + magic-byte check as an upload; `mime`, `kind` and `encrypted` come from that check, never from the JSON. Every JSON record is validated with the same rules as normal input, IDs are format-checked, and all rows get the new instance's `org_id`s. Files are written through the normal storage service, so the target instance's file encryption setting (D-007) applies and `encrypted` reflects what was actually done.
    - **Limits (zip bomb):** max. entry count, max. size per entry and total uncompressed size (default: 2× the manifest total, hard cap configurable) and max. compression ratio per entry; free disk space checked first.
    - **Schema version:** `manifest.json` carries app and schema version. Same or **older** schema → import, then run `migrate`; **newer** → refuse with "Dieses Backup stammt aus DocHamster X.Y – bitte zuerst auf diese Version aktualisieren".
    - Encrypted ZIPs ask for the password on the console (never as an argument, so it doesn't land in the shell history).
  - **Server backup (for the operator, docs + CLI):** `php artisan dochamster:backup` writes a consistent database dump (`mariadb-dump`/`mysqldump --single-transaction`, no downtime) plus the storage folder to a target folder. DB credentials reach the dump tool via a temporary `--defaults-extra-file` (mode 0600, deleted afterwards), never on the command line (visible in the process list); output is created with umask 077; a target inside the storage or `public/` folder is refused; backup temp files, restore staging and unfinished uploads are not copied; schedulable via cron. Needs `proc_open` and the dump binary; where they are missing (some web hosting), `dochamster:doctor` shows "Server-Backup nicht verfügbar – nutze die Datenbank-Sicherung deines Hosters" and the command refuses with the same text (Q-15, Lead, 2026-10-29, under the operator rule of AGENTS rule 6). No own PHP dumper: hosters back up their databases anyway, and the admin-page export works everywhere. This is the disaster-recovery backup; the admin-page export is the user-facing one. Docs explain both and that the app key (`.env`) must be kept separately – without it encrypted fields can't be read.
  - **PLAN impact:** §4.8 "Datenexport (DSGVO Art. 20)" is covered by this export; new acceptance criteria and §12 backup text – see PLAN-REVIEW B22.

### D-024 · Guided setup for non-technical users: setup wizard in the browser + shell install — Owner: PO (requirement), Lead (technical design)
- **Status:** requirement decided (PO, 2026-10-29); technical design open for the Lead (Q-12)
- **Requirement (PO):**
  - Assume the person installing DocHamster has **little technical knowledge**.
  - The main way to install is a **setup wizard**: a page the user opens in the browser that leads through the whole setup **step by step** and explains every step in plain German – server check, database, owner account, mail, background jobs, **connecting the phone** (incl. putting the app on the home screen), first steps.
  - The wizard **sets up the database itself**. Where needed it asks for the database credentials (host, port, database name, user, password), tests them and creates the tables.
  - A **shell installation** stays available as an alternative (own servers, technical users).
- **Consequence for D-010:** "upload/clone, `composer install`, `.env`, `dochamster:setup`, cron" is no longer the standard path for the target user, because it needs a shell. The wizard has to work for someone who can only upload files and open a web address. D-010's minimum requirements (incl. the fixed HTTPS domain) stay.
- **Questions for the Lead (Q-12)** – technical design, decided by the Lead itself (AGENTS rule 6 since 2026-10-29); only product-level points go to the operator:
  1. **Package without Composer:** a ready-to-upload release ZIP including `vendor/`, built by CI for every release? (Changes D-010's install path.)
  2. **Securing a fresh instance:** before setup, anyone who finds the address could run the wizard and take the instance over. How does the installer prove it's their server without a shell – e.g. a one-time setup code that the wizard writes into a file the user opens with the hoster's file manager/FTP, or that the shell install prints? The wizard must lock itself for good once finished.
  3. **Writing the configuration:** the wizard needs to store DB credentials, app key, URL and mail settings. Write `.env` (web server needs write access once, then lock it down?) or another place? What happens to file permissions afterwards?
  4. **Database:** test the connection with clear error messages (wrong password, host unreachable, missing rights), create the database if the user has the right, run migrations within web-hosting time limits; MariaDB/MySQL only (D-003). Before the DB exists, sessions/cache can't use the database driver – how does the wizard run until then?
  5. **Cron:** on web hosting the user creates the cron job in the hoster's control panel – the wizard explains it and confirms via the heartbeat (D-010). What if a hoster has no cron at all?
  6. **Owner account and phone:** these steps depend on P1-4 (passkeys, pairing). Order of steps, and what the wizard shows so the phone gets connected and the app lands on the home screen (iPhone/Android differ, B14).
  7. **HTTPS/domain:** on web hosting the hoster provides the certificate – the wizard can only check and explain. Should the shell install on an own server also set up the certificate (e.g. Let's Encrypt)?
  8. **Shell install – scope:** an interactive `php artisan dochamster:setup` that asks the same questions (incl. DB credentials) and/or an `install.sh` for Debian/Ubuntu that also installs PHP, MariaDB and the web server?
- **Plan:** PLAN §4.9 (acceptance criteria), §12, §14 (P1-9…P1-11).
- **Changed 2026-10-29 (P0-15):** routing of Q-12 adapted to the new AGENTS rule 6 (Lead decides technical questions); content unchanged.

### D-025 · When the minimum PHP version is raised — Owner: Lead
- **Status:** decided (Lead, 2026-10-29, under the operator rule of AGENTS rule 6; Q-14, Manager review of PR #5 point 11)
- **Decision:** we follow the PHP version of the current **Debian stable** release and never go below 8.4 (D-002). When a new Debian stable ships a newer PHP, the minimum is raised – **before 1.0 in any release, from 1.0 only in a major release**, so an unattended minor update never breaks an install. Announced in the CHANGELOG; `dochamster:doctor` warns one release ahead; the update steps stop with a clear message if PHP is too old.
